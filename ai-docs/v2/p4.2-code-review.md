## 1. 审阅发现与处置

| 编号 | 级别 | 发现 | 处置 |
| --- | --- | --- | --- |
| **H1** | **H** | `last_settle_at` 建为 naïve `TIMESTAMP`，用 `CURRENT_TIMESTAMP` 写入（DB 会话时区 UTC），而 node-postgres 把 naïve 串按 **进程本地时区(+08)** 解析 → 新角色一创建即「离线 8 小时」，status/pendingHours 全部虚高 | **已修**：迁移为 `TIMESTAMPTZ`（schema `@db.Timestamptz(6)`）+ init-db 幂等 DO 块将既有 naïve 列按 UTC 转换；冒烟 pendingHours≈0、pendingKills=0 回归通过 |
| **H2** | **H** | `12 × (60/100) × 60 = 431.999…` → `floor` 得 431，离线满 12h 少算 1 杀 | **已修**：改为整数顺序 `floor(h × rounds × pct / 100) = 432`；`effectiveHours` 单独四舍五入展示 |
| M1 | M | 结算落两处（game_idle_counters 计数 + characters.last_settle_at 锚点），无法同事务；中途异常可能其一只未写 | 接受：先结算产出、再写计数、最后刷锚点（失败时偏向玩家，最多多计入少量额度）；P5 批量结算引入幂等键 |
| M2 | M | status.estimatedLingyun 按角色境界模板估算，非实际结算单位 | 接受：status 仅是预估，契约已注明 |
| M3 | M | 无可结算收益时返回 `success:true, kills:0`（非错误码） | 契约一致；避免轮询报错 |
| L1 | L | `game_idle_counters.day` 用 DB `CURRENT_DATE` 分桶，跨时区以 DB 时区为准 | 文档化 |
| L2 | L | 生产运行时因 ionet-ts 模块限制无法以 `NODE_ENV=production` 启动 → 生产守卫仅代码路径核对 | 与既有 dev 门禁（unit/kill、currency/grant）同一写法；已核对 |
| L3 | L | BIGINT（lingyun/spirit_stones）→ Number 精度债 | 继承登记 |

## 2. 关键正确性核对

- **公式**：`有效小时 = min(elapsed,12) × 60%`，`击杀 = floor(有效小时 × 60)`；hours=12 → 432 杀、effectiveHours=7.2（实测）。
- **日上限**：首次结算物品 ≤200 且 `dailyItemsProduced == itemsProduced`；第二次仅补足到 200（`itemsProduced == 200 − 首次`）；第三次 `itemsProduced=0`、计数维持 200；三次灵韵均 ≥ 2160（封顶只限物品，不影响灵韵）。
- **锚点语义**：无 hours 且 elapsed≈0 → `暂无可结算收益`、kills=0、锚点不刷新（status.pendingHours 仍≈0）。
- **抽取重构**：`kill` 与 `settleKills` 拆分后响应形状不变（新增 itemsProduced 字段），P4.1 击杀回归通过。
- **参数/单位**：非敌对 → NOT_KILLABLE；非法 code → UNIT_NOT_FOUND；hours<0 → INVALID_PARAM；hours 覆盖仅非生产。
