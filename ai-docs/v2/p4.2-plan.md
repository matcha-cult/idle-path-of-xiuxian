# P4.2 实施计划 — 离线收益（放置循环第一批）

> 依据：v2 设计 §9.2 / §9.3；P4.1 已交付单位与掉落结算，本批接入「离线按效率继续结算」
> 状态：执行中

---

## 1. 范围收敛（批决策）

| 决策 | 结论 |
| --- | --- |
| 离线公式 | `有效小时 = min(离线小时, 12) × 60%`；`击杀数 = floor(有效小时 × 每时轮数)` |
| 轮数 | config `idleRoundsPerHour = 60`（等价 1 杀/分钟），可调 |
| 日上限 | config `idleDailyItemCap = 200` 件/日；达到上限后仅停发物品，灵韵/通货/精华照常 |
| 计时锚点 | `characters.last_settle_at`（新增列，默认当前时间；结算成功即刷新） |
| 日计数 | 新表 `game_idle_counters(character_id, day, items_produced)`，UNIQUE(character_id, day) |
| 结算单位 | 请求带 `unitCode`（当前秘境/目标单位）；须为 hostile |
| 结算复用 | 抽取 P4.1 `settleKills` 核心，kill 与 idle 共用；idle 传 itemBudget |
| `hours` 覆盖 | 仅非生产环境可用（生产 → FORBIDDEN），便于冒烟；生产恒按真实 elapsed |
| 秘境层数/推进 | 归 P5 放置循环（本批不做）；炼丹继续顺延 |
| 幂等 | 结算以 `last_settle_at` 为界，重复调用不重复计入（elapsed 归零） |

## 2. 数据变更

- `characters.last_settle_at TIMESTAMP(6) NOT NULL DEFAULT CURRENT_TIMESTAMP`（init-db.mjs 幂等 ALTER + schema.prisma）
- `game_idle_counters`（game 库；init-game-db.mjs，表数 18 → 19）

## 5. API（契约详见 p4.2-api-contract.md）

- GET  /api/game/idle/status — 待结算时长/预计击杀与灵韵/今日物品计数
- POST /api/game/idle/settle {unitCode, hours?} — 离线结算；hours 仅开发环境

## 6. 冒烟清单

1. 新建角色 → status 显示 lastSettleAt 非空、pendingHours≈0
2. `settle {hours: 12}` → kills = floor(12×0.6×60)=432；灵韵按单位境界模板 ×432；日物品计数 ≤200
3. 同角色再次 `settle {hours: 12}` → 日物品计数达到/不超过 200（第二次物品产出被截断，灵韵仍增）
4. 无 hours 且 elapsed≈0 → 不结算且 `last_settle_at` 不刷新（无收益不消耗计时）
5. 生产守卫：NODE_ENV=production 时 hours 覆盖 → FORBIDDEN（代码路径核对）
6. 非敌对单位 → NOT_KILLABLE；非法 unitCode → UNIT_NOT_FOUND
7. status 的 estimatedKills 与 settle 实际 kills 一致（同 elapsed 下）
8. health 200 + P4.1 击杀回归通过

## 7. 风险 / 技术债

- 离线只结算「单一目标单位」，尚无多秘境轮换/层数收益曲线 → P5。
- 日上限在 game 库按 DB 日期（CURRENT_DATE）统计；跨时区以 DB 时区为准。
- `last_settle_at` 与日计数为两处写入（characters + game_idle_counters），无法同事务（跨池同一物理库但分属两个 pg Pool）→ 若中途异常可能计数或计时其一未更新；P5 批量结算时引入幂等键修正。
