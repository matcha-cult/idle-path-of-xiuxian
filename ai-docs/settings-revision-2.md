## 0. 本轮要固定的四件事

本轮的动因是：**地图 / 战斗 / 挂机战斗 / 剧情四者的关系没有定稿**，导致
「在哪打、为什么打、什么能挂着打、剧情管什么」四个问题都没有唯一答案。
本轮只做一件事：**给这四者立一条闭合的因果链**，其余数值与内容填充留到后续轮次。

### 0.1 用户给定的骨架（逐字，本轮的最高约束）

> 地图中发现可挂机的秘境，在线战斗探索秘境，解锁之后允许离线挂机。
> 地图本身有挂机点。解锁下一个地图是需要剧情的。
> 主线起点就按初入「青云宗」开始，第一、二章剧情在青云宗，第三章下山历练，
> 第四、五章引出世界之外的混沌，第五章结束离开当前大世界进入混沌海。

### 0.2 由骨架推导出的核心循环（本轮确立）

```
        ┌──────────────── 地图 M（剧情解锁）────────────────┐
        │                                                   │
   挂机点 A ──┐                                        ┌── 秘境 X
   挂机点 B ──┤  进图即可挂（无门槛、收益稳）             │   ① 发现 → ② 在线探索
              │                                        │        → ③ 解锁后离线挂机
              └──────────► 离线结算目标 ◄──────────────┘
                                 │
                     满足剧情条件 → 解锁地图 M+1
```

一句话口径：**地图是容器，挂在挂机点、战在秘境；秘境要在线打出来才能离线挂；
地图靠剧情推。** —— 离线时间**只能换产出，不能换进度**。

### 0.3 与现有实现的距离（先说清欠账）

| 概念 | 现状 | 本轮要求 |
| --- | --- | --- |
| 地图 | **不存在**。27 张表里只有 `game_zones` 平铺，靠 `order_index` 线性排队 | 新增一层容器 |
| 秘境解锁 | 只有 `require_prev_best_floor` 的**链式层数门槛**，没有「发现/在线探索/解锁挂机」三态 | 三态状态机 |
| 挂机点 | **不存在**。挂机目标是 `game_zone_state.current_zone_id`（直接挂当前秘境） | 新增挂机点 + 目标可为挂机点或秘境 |
| 在线 / 离线区别 | **没有区别**。`idle.settle` 直接按离线小时结算，秘境层数只由 `zone.challenge` 推进 | 离线只结算**已解锁**目标 |
| 战斗 | `combat.spawn` / `combat.kill` 是**dev 接口**（07 号清单标注），非玩法入口 | 战斗由秘境探索驱动 |
| 章节 | 5 章已入库（`game_chapters`），结构与本轮不同（见 R2-5） | 重定章名与地图归属 |

## 1. 修订条目

### R2-1 新增「地图」层：秘境与挂机点的容器，由剧情解锁

**原文（§9.1 / §10 / P5.1）**：
- 核心循环写的是「进入秘境(关卡) → 自动战斗结算」（§9.1），**没有地图这一层**。
- 秘境是平铺的：`game_zones` 有 `chapter` / `order_index` / `min_realm` /
  `require_prev_best_floor`，解锁是「上一秘境 bestFloor 到阈值」的链式推进。
- 系统解锁阶梯（§10）是按**章节**排的，不是按地图。

**修订**：

1. **新增「地图」作为玩法容器**。一张地图是一个可进入的区域，内含：
   - **若干挂机点**（进入地图即可挂，无探索门槛）；
   - **若干秘境**（每张地图至少 1 个，需经历 R2-3 的三态）。
2. **地图解锁的闸门是剧情，不是境界也不是战力**：
   - 地图 M+1 的解锁条件 = 与 M+1 绑定的**章节剧情完成**；
   - 境界 / 战力只作为**地图内部**秘境与挂机点的门槛（`min_realm` / 战力曲线），
     不用来卡地图本身 —— 这样「卡关」永远表现为「剧情没推完」而不是「数值不够」，
     与放置游戏「不让玩家干等数值」的取向一致。
3. **世界推进是线性的**：地图按 `order_index` 单向推进，本轮**不做**开放式大地图
   与自由选图（混沌海终局的领地争夺除外，见 R2-5）。
4. **地图与章节不是 1:1**（这是本轮的关键结构决定）：
   - **地图 1 · 青云宗** 覆盖 **第一、二章**（外门 → 内门/后山）；
   - **地图 2 · 山下凡尘** 覆盖 **第三章**（下山历练）；
   - **地图 3 · 混沌裂隙** 覆盖 **第四、五章**（混沌渗透 → 离开大世界）；
   - **地图 4 · 混沌海** 是**终局大世界**（对应 §7.4 混沌争夺战）。
   即：**一张地图可以承载多章**，章节是剧情节拍，地图是玩法空间。

**影响范围**：

- 新增表 `game_maps`：`code` / `name` / `order_index` / `requires_map_code` /
  `unlock_chapter_code`（剧情闸门）/ `min_realm` / `description` / `sort`。
- 新增表 `game_map_progress`：`character_id` / `map_id` / `status`
  （`locked` / `available` / `current`）/ `unlocked_at`。
- `game_zones` 新增 `map_id`（秘境归属地图）；`game_zones.chapter` 语义收窄为
  「首次出现于第几章」，不再承担解锁职责。
- `game_chapters` 新增 `map_code`（章节归属地图，与 R2-5 的章名表同步改 seed）。
- 服务侧：新增 `map.service`（列表 / 进入 / 解锁判定）；
  `chapter.service` 完成章节时**触发地图解锁判定**（复用现有 `game_chapter_progress`）。
- 协议侧：新增 `map.list` / `map.enter`；`zone.panelUpdate` 与 `idle.status` 需带出
  `mapCode` 供 UI 分组。
- UI 侧：`panel-registry` 新增「地图」域（候选 key `map`，图标 `GlobalOutlined`），
  秘境面板按地图分组、挂机面板的目标选择器需要跨「挂机点 + 已解锁秘境」两类。

**待明确**：
1. 上面 4 张地图的**命名与切分**是否认可？（尤其「地图 3 覆盖 4-5 章」是否要拆成两张图）
2. 地图内是否要「区域（子地图）」再分一层？（如青云宗 = 外门 / 内门 / 后山）
3. 「进入地图」这一动作本身是否有成本（传送符 / 灵韵 / 无成本）？
4. 已解锁的地图能否**回退**去挂低级图？（§8.2 说低级副本无递减惩罚 → 倾向可以）

### R2-2 挂机点：地图上的直接挂机位（无需探索）

**原文**：无。原设计只有「秘境(关卡)」一种可挂机对象（§9.1）。

**修订**：

1. **挂机点（idle spot）是地图内的安全挂机位**，玩家进入地图即可挂，**不需要探索**。
2. 挂机点的定位是**保底与稳态**，不是最优解：
   - 收益**稳定**、门槛低（只受地图与 `min_realm` 限制）；
   - 单位时间产出**低于**同地图已解锁的秘境 —— 因为秘境需要在线探索投入。
   - 这样形成取舍：**没时间在线 → 挂机点；在线打通过 → 秘境挂得更肥**。
3. 挂机点**不推层**（没有 floor 概念），产出按「每小时轮数 × 单位轮产出」线性结算，
   与现有 `idle` 公式同构（§9.2）。
4. 同一时刻**只能有一个挂机目标**（挂机点或秘境），本轮不做多目标并行挂机。

**影响范围**：
- 新增表 `game_idle_spots`：`code` / `name` / `map_id` / `min_realm` / `unit_code` /
  `drop_table_code` / `lingyun_per_hour` / `tier_offset` / `order_index`。
- `game_zone_state` 推广为「当前挂机目标」：新增 `target_type`（`zone` / `idle_spot`）
  与 `target_id`，`current_zone_id` 保留兼容或迁移。
- `idle.service` 结算入口需要按目标类型分流（挂机点无层数概念）。
- UI：挂机面板的目标选择器；地图面板内挂机点的展示与「设为挂机目标」。

**待明确**：
5. 一张地图配**几个挂机点**？（建议 1~3，且与地图主题相关，如青云宗 = 山门石阶 / 后山药圃）
6. 挂机点与同级秘境的**产出比例**：方向 ✅ **已拍板：挂机点 = 保底稳定位**（见 §4.1），
   具体比例仍待定（如 40%~60%）
7. 挂机点是否也有**日产出上限**共享现有「200 件/日」（`game_idle_counters`）？
8. 挂机点产出的**底材 T 阶**如何定？（建议 = 所属地图的 T 阶范围，见 R2-6）

### R2-3 秘境三态：发现 → 在线探索 → 解锁离线挂机（**本轮的核心**）

**原文（§9.1 / P5.1 / P5.2）**：
- 「进入秘境(关卡) → 自动战斗结算 → … → 离线期间按效率继续结算」——
  即：**只要能进，就能离线挂**，在线与离线没有玩法差别。
- `game_zone_progress` 只有 `floor` / `best_floor` / `cleared`，没有解锁状态。

**修订**：

秘境对角色有**三个状态**，只能单向推进：

| 状态 | 可见性 | 能否在线探索 | 能否离线挂机 |
| --- | --- | --- | --- |
| ① 未发现 `hidden` | 地图上不可见（或在图上显示为未知区域） | 否 | 否 |
| ② 已发现 `discovered` | 可见，可查看门槛与产出 | **是（唯一能推进状态的途径）** | **否** |
| ③ 已解锁 `idle_unlocked` | 可见，可设为挂机目标 | 是（继续推层） | **是** |

**关键机制（本轮最重要的设计决定）**：

> **离线时间只能兑换产出，不能兑换进度。**

- 未解锁的秘境，**离线期间不推进任何探索进度**；
- 已解锁的秘境，离线只按已达成的最深层数结算产出。
- 因此「在线探索」有了不可替代的价值 —— 这正是放置游戏里「在线做什么」的答案。

**在线探索的形态**：

1. **自动战斗，不需要手动操作**（本作是放置游戏；§7.3 的「任务不需要主动接取」同理）。
   在线时玩家看到的是**实时推进与战报**，而不是需要手指介入的战斗。
2. 探索按**层（floor）**推进，沿用现有 `game_zones` 的曲线：
   `base_power + power_step × (floor-1)` 与玩家战力对照，战力不足即卡层。
3. 每 `boss_every_floors` 层出现 `boss_code`，击败 Boss 才算通过该段（可继续复用
   `max_floor` / `cleared`）。
4. **解锁条件（提议）**：击败该秘境的**第一个 Boss**（即
   `boss_every_floors` 层）即置为 `idle_unlocked`；之后继续在线深入可提升挂机收益
   （`lingyun_bonus_per_floor` / `tier_bonus_every_floors` 已实现）。
5. **战斗中禁止突破**（R1-1 已定）在本轮继续成立：探索过程中不允许触发境界突破。

**发现（discovery）的触发**：本节建议**进入地图即发现该地图的所有秘境**（地图内秘境
列表直接可见、逐个需要在线打通），理由：
- 与 PoE「进图即知道有哪些区域」的直觉一致，也与 R1-3「任务不需接取、进区域自动触发」同构；
- 避免「找不到秘境」的搜索成本 —— 放置游戏的乐趣在取舍，不在找路。
- 若希望保留探索感，可退化为「发现 = 完成该地图的第一个挂机点达到 N 小时」
  （见待明确 10）。

**影响范围**：
- `game_zone_progress` 新增 `discovered_at` 与 `idle_unlocked_at`（或 `status` 枚举），
  并保留 `floor` / `best_floor` / `cleared` 语义不变。
- `zone.service`：
  - 新增「在线探索推进」路径（区别于现有 `zone.challenge` 的单次挑战）；
  - `zone.list` 按状态过滤（`hidden` 不下发）；
  - 新增「设为挂机目标」的前置校验：**必须 `idle_unlocked`**。
- `idle.service`：结算前校验目标已解锁；未解锁直接业务失败（新错误码，
  如 `ZONE_NOT_IDLE_UNLOCKED`）—— 这条校验是**防止离线刷进度**的唯一闸门，必须有单测。
- `edge`：在线探索的实时推进需要推送（复用 `broadcastNotification` / `sendNotification`）。
- UI：秘境面板从「平铺列表」改为**按地图分组 + 三态徽标 + 探索进度**；
  未解锁的秘境禁用「设为挂机」并给出原因（`LockedHint` 已具备）。

**待明确**：
9. **在线探索的推进速率** —— ✅ **已拍板：自动实时推进**（见 §4.1 与 §4.2 的 tick 模型）
10. 「发现」到底怎么触发？（建议进图全可见；备选：挂机点时长达标 / 剧情触发 / 探灵道具）
11. **解锁离线挂机的条件** —— ✅ **已拍板：击败该秘境第一个 Boss**（见 §4.1）
12. 一个秘境**通到顶（`max_floor`）之后**留下什么？（重复挂机产出 / 掉落池升阶 / 无事可做）
13. 在线探索是否有**消耗**（体力 / 时间 / 通货）？还是纯战力门槛？

### R2-4 战斗玩法的定位：由秘境探索驱动，不再是 dev 接口

**原文（07 号清单 / P4）**：
- `combat.spawn` / `combat.kill` 被标注为 **dev 接口**；
- 掉落来自「秘境关卡 × 物品基底 × 稀有度」配置（§4.7）。

**修订**：

1. **战斗的唯一玩法入口是秘境探索**（R2-3）。`combat.spawn/kill` 的 dev 接口**保留**
   （开发者工具仍然需要），但**不再承担玩法职责**，UI 上只出现在设置域的开发者工具里。
2. 战斗**全自动**，玩家做的是「选哪个秘境、挂多久、要不要换目标」这类决策，不做操作。
3. **单位与地图绑定**（衔接 R1-2 与 v2 §4）：
   - 地图决定**单位境界区间**与**底材 T 阶区间**；
   - 秘境决定**具体单位模板与隐藏词条池**（`game_unit_hidden_pools` 已实现）；
   - 挂机点是同一地图里**更弱的单位组合**（对应「保底」定位）。
4. **中立 / 友方单位目前不可交互**（`unit.service.ts:445` 对非 `hostile` 直接拒绝击杀）。
   本轮**明确**：地图内的中立/友方单位只作为**叙事与场景存在**（对话、任务触发点），
   不参与战斗；其可玩交互留到后续轮次（避免本轮范围失控）。

**影响范围**：
- `zone.service` 承担探索战斗编排；`combatStore` 的前端职责从「图鉴+dev 操作」收敛为
  「图鉴 / 掉落表查询」（面板已实现，本轮只需去掉 dev 入口在玩家面板的暴露）。
- 单位种子的 `camp` 字段语义确认：地图内可刷单位 = `hostile`。
- 需新增「地图 → 单位境界区间」的配置来源（地图表或秘境表，见待明确 14）。

**待明确**：
14. 单位境界区间挂在**地图**上还是**秘境**上？（建议秘境，因为同地图内可以有难度梯度）
15. Boss 的定位：每 `boss_every_floors` 层的常规 Boss 之外，是否需要**地图级终局 Boss**？
16. 死亡 / 失败的后果是什么？（§8.2 说灵韵不因失败损失 → 失败只是不推进？）

### R2-5 剧情重定：章节结构、地图归属与「混沌海」终局

**原文（§7.1 / §7.4）**：

| 章 | 主题 | 境界 | T 阶 |
| --- | --- | --- | --- |
| 第一章 | 初入仙途 | 1~3 | T1~T3 |
| 第二章 | 下山历练 | 4~6 | T3~T6 |
| 第三章 | 秘境夺宝 | 7~9 | T6~T9 |
| 第四章 | 大劫将临 | 10~12 | T9~T12 |
| 第五章 | 飞升前夜 | 13~14 | T11~T14 |

**修订**（按用户给定骨架）：

| 章 | 地图 | 主题 | 对应境界 | 底材 T 阶 |
| --- | --- | --- | --- | --- |
| 第一章 | 地图 1 · 青云宗（外门） | 初入青云宗 | 1~3 境 | T1~T3 |
| 第二章 | 地图 1 · 青云宗（内门/后山） | 宗门修行 · 初识仙途 | 4~6 境 | T3~T6 |
| 第三章 | 地图 2 · 山下凡尘 | **下山历练** | 7~9 境 | T6~T9 |
| 第四章 | 地图 3 · 混沌裂隙 | **世界之外的混沌（引出）** | 10~12 境 | T9~T12 |
| 第五章 | 地图 3 · 混沌裂隙（深处） | 直面混沌 · **离开当前大世界** | 13~14 境 | T11~T14 |
| 终局 | 地图 4 · 混沌海 | 混沌争夺战（§7.4 保留） | 14 境后 | 全量 |

要点：

1. **起点固定为「初入青云宗」**；第一、二章的剧情、秘境、挂机点**全部发生在青云宗内**
   （外门 → 内门/后山），因此**地图 1 承载两章**（R2-1 第 4 条）。

### 4.1 已拍板（2026-09-13）

**D1 + D2 的直接后果：Boss 是「进度闸门」，层数是「收益刻度」。**

- 没过第一个 Boss → 秘境**只能在线打**，不能挂；
- 过了第一个 Boss → 解锁离线挂机，收益按**已达成的最深层数**结算；
- 想提高挂机收益 → 只能继续**在线**深入 → 在线动机持续存在，而不是「解锁完就再也不上线」。

**D3 的后果：挂机点与秘境是互补而非替代** —— 挂机点是「没时间上线时的稳态底座」，
秘境是「收益更高但要用在线时间换」的进取位。

### 4.2 在线探索的 tick 模型（D1 的落地细化）

**「在线」怎么判定**（这条决定整个防刷设计）：

> **在线 = 存在一条活着的 WS 会话（应用层心跳未判死）。**

于是「离线不推进进度」**不需要任何额外的时间戳计算** —— 现有 `system.ping (1,1)`
的 15s/10s 判死机制天然给出了在线窗口：会话断开或判死后，服务端不再推进探索。
这也是本设计唯一需要借力的既有机制，同时**避开**了「由客户端上报在线时长」这种可伪造口径。

再叠一层：**页面不可见（`visibilitychange` → hidden）不计入在线探索**。
否则玩家前台挂一夜标签页就等于「离线也能刷进度」，与 D1 的意图直接冲突。
代价是切去别的页面会暂停进度 —— 对放置游戏可接受，且客户端已实现该生命周期。

**推进节拍**（服务端权威，客户端只渲染推送帧）：

| 步骤 | 内容 |
| --- | --- |
| 1 | 每 tick（对齐现有 1s metrics 轮询）按「战力碾压比」结算本轮击杀数 |
| 2 | 按掉落表判定产出（灵韵 / 物品），并走现有辨宝法阵筛选 |
| 3 | 累计当前层击杀数 → 达标则 `floor + 1` |
| 4 | `floor` 命中 `boss_every_floors` → 进入 **Boss 层**：Boss 未被击败前不涨层 |
| 5 | 击败**第一个** Boss → 置 `idle_unlocked` 并推送解锁提示（D2） |
| 6 | 战力不足（`playerPower < base_power + power_step × (floor-1)`）→ **卡层**：不再涨层，改为原地刷当前层（仍有产出、无进度），UI 给「战力不足，还差 N」 |

**明确不做**（防止范围失控）：

- 客户端**不本地涨层、不本地算产出** —— 否则与服务端权威冲突，且离线刷的口子会重开；
- 不做任何形式的「离线补算探索进度」，**包括**「登录时按离线时长一次性推进」。

### 4.3 由 D1/D2/D3 反推出的两个新问题

1. **挂机收益是锁定在「解锁那一刻的最深层数」，还是随在线深入实时提高？**
   → ✅ **已拍板 D5：实时提高**（挂机结算时读当前最深层数）。否则玩家会在解锁后
   「先挂满再深入」，节奏被拧成「先躺后打」，与 D1 想要的方向相反。
2. **现有 `zone.challenge`（单次挑战接口）在新模型下是什么？**
   建议**降级为开发者工具**（与 `combat.spawn/kill` 同处理），玩家侧只保留
   「在线自动探索」这一条路径 —— 否则同一件事有两个入口，状态机必然分叉。
   （仍待拍板；注意 R2-7 若采用固定等级节点模型，`zone.challenge` 会被节点推进取代。）

## 5. R2-7 地图线路图与传送点（PoE 参照）

### 5.1 用户要求（逐字）

> poe 中是有跑图环节，每个图的怪物等级固定，我希望你参考该设定设置类似的地图线路图，
> poe 中，大部分图有传送点，解锁传送点之后可通过传送点快速抵达，我希望你也参考该设定。

### 5.2 修订：把「地图」从容器升级为「线路图」

R2-1 把地图当**容器**（内部平铺若干挂机点与秘境）。按 5.1 的要求，地图内还要有
**跑图环节**，因此地图 = **节点线路图（graph）**：

- **节点（区域 area）是地图的基本单位**，玩家在节点之间移动（跑图）。
- **每个节点的怪物等级固定**，不随层数或时间变化。这直接决定两件事：
  1. 该节点可掉落的**底材 T 阶**（与 R1-6「怪物只能掉落自身境界 T 阶的底材」完全一致）；
  2. 该节点的**战力门槛是固定值**（不是随层数上涨的曲线）。
- **节点按线路连接**，形成**有分支**的推进图（不是一条直线），玩家可自选路线。
- **传送点（waypoint）**挂在部分节点上：
  - **首次到达**该节点即解锁其传送点；
  - 解锁后可从任意已解锁传送点**直达**该节点，跳过跑图；
  - 未解锁的节点在图上显示为「未探索」。

> 因此 §1 R2-3 的「待明确 10（发现怎么触发）」被本节直接改写：
> **秘境 = 线路图上的特定节点，到达即发现**。原先建议的「进图全可见」不再适用 ——
> 发现由**跑图**承担，这比「一进图就全知道」更贴合用户要的探索感。

### 5.3 节点类型：把「挂机点」与「秘境」统一成一种实体

R2-1 的秘境与 R2-2 的挂机点，在本节统一为**同一种实体（地图节点）**，用 `kind` 区分：

| `kind` | 说明 | 可否挂机 |
| --- | --- | --- |
| `idle_spot` | 挂机点（到达即可挂，保底稳定位，D3） | 是，**无需探索** |
| `secret_realm` | 秘境（需在线探索，击败首个 Boss 后解锁离线挂机，D2） | **解锁后**才可 |

传送点不是第三种 `kind`，而是节点上的一个标记 `has_waypoint`（一个秘境节点也可以带传送点）。

**数据模型**：

- `game_map_nodes`：`code` / `map_id` / `name` / `kind` / `level`（怪物等级，固定）/
  `min_realm` / `unit_code` / `boss_code` / `drop_table_code` / `has_waypoint` /
  `order_index` / `description`。
- `game_map_edges`：`map_id` / `from_node_id` / `to_node_id` /（是否双向）——
  线路图的邻接表。
- `game_node_progress`：`character_id` / `node_id` / `visited` / `waypoint_unlocked` /
  `idle_unlocked` / `cleared`。

> 这取代了 R2-2 里单列的 `game_idle_spots`：挂机点与秘境同表，只差 `kind`，
> 避免「两种节点两套进度表」的重复。

### 5.4 与层数模型的关系（**修正：不冲突**，两者是不同层级的分工）

> 用户澄清：**「地图上分布秘境，秘境有层数，这个貌似不冲突。」**

**此前的判断下重了，此处更正。** 地图层与秘境的内部层数是**两个不同层级**的结构，
可以共存 —— 地图层管「在哪打、怎么走过去」，秘境层管「进去之后打多深」：

| 层级 | 承担什么 | 等级 / 门槛 |
| --- | --- | --- |
| **地图层（线路图）** | 跑图推进、传送点、挂机点、发现秘境入口 | 节点**怪物等级固定** |
| **秘境层（内部）** | 秘境内的逐层深入与产出、Boss 层 | 秘境**最多 3 层**（见 §5.6），层内小幅递进 |

于是 T 阶与难度的**主要**晋升来自「沿线路图走到更高等级的节点」；
秘境内部的 3 层只做**小幅递进** —— 这恰好解释了为什么 `power_step` /
`tier_bonus_every_floors` 这类「逐层递进」的字段在 3 层规模下只是**微调手段**，
而不是承担 T 阶晋升的主力。

**因此现有实现不用推翻，只做加法与收紧**：

| 现有实现 | 处置 |
| --- | --- |
| `game_zones`（秘境本体） | **保留**，新增 `map_id`（归属地图）与「入口节点」 |
| `game_zones.max_floor` | **保留语义**，seed 收紧到 **≤3**（§5.6） |
| `game_zones.base_power` / `power_step` | **保留**：3 层内的小幅递进仍然需要 |
| `game_zones.boss_every_floors` | **保留**，但在 3 层规模下需重新给值（见 §5.6） |
| `game_zone_progress`（floor / best_floor / cleared） | **保留**；再加 `discovered_at` / `idle_unlocked_at`（R2-3 的三态） |
| `game_zone_state.current_zone_id` | 推广为「当前挂机目标」（可指向秘境或挂机点） |
| `zone.service` / `ZonePanel` / `IdlePanel` / HUD 的「秘境·层」 | **全部保留**，层数语义不变 |

> **原先列出的「三张表重构 + `zone.service` 重写 + 11 个面板返工」作废。**
> 本轮是**新增地图层**，不是替换秘境层。这也把 §2 实施顺序里最贵的一段风险去掉了。

**唯一需要留意的残留问题**（不是冲突，是取值）：R1-6 的「怪物只能掉落自身境界 T 阶的
底材」在 3 层秘境里仍然成立 —— 只要把秘境的**节点等级**与 3 层的 `power_step` 取在
同一 T 阶区间内即可，不需要 `tier_bonus_every_floors` 去跨 T 阶。

### 5.5 秘境的数量与层数上限（用户补充）

> 用户：**「按每个地图最多 1 个秘境，最少 0 个算，每个大世界内秘境最多 3 层。」**

- **每张地图的秘境数量 = 0 ~ 1 个**。这条把地图的玩法密度重心**明确挪到**
  **跑图节点 + 挂机点 + 传送点**上：秘境是这张图的**压轴目标**，不是刷怪场。
  - 这反过来**强化了 D2**：「击败首个 Boss 才解锁离线挂机」发生在这张图的**核心目标**上，
    而不是发生在随便一个刷子副本上 —— 闸门的分量对了。
- **秘境层数上限 = 3 层**（大世界内）。相对现有 `max_floor` 属于**收紧**：
  秘境是「三段式短副本」，不是无限爬塔。3 层的节奏建议为：
  第 1 层铺垫 → 第 2 层加压 → 第 3 层 Boss（= D2 的解锁点）。
- **0 个秘境的地图是合法形态**：这类地图靠**跑图 + 挂机点**承担玩法，
  适合作为过渡图（例如第 3 章「下山历练」这种以赶路与见闻为主的一章）。
- 由此需要重给 `boss_every_floors` 的值：3 层规模下应为 **3**（第 3 层即 Boss 层），
  而不是现有的默认 10。

## 6. R2-8 战斗结算规则（确定性战力模型）

### 6.1 现有地基（照抄事实，不发明）

本轮不另起一套战斗，而是在**已有的确定性检定**上补齐「速率」与「词条作用面」：

| 事实 | 出处 |
| --- | --- |
| 战力公式 `playerPower = 境界×20 + 已装备数×5 + floor(功法等级和 / 2)` | `zone.service.ts:60-75`，权重来自 `APP_CONFIG.zonePower` |
| 胜利条件是**确定性检定**：`playerPower ≥ basePower + (floor−1)×powerStep` | `zone.service.ts:6` 注释 |
| 每杀产出灵韵 `realmLingyun(单位境界)`，仅当 `gives_lingyun` | `unit.service.ts:219` / `:472` |
| 掉落按 `dropsPerKill` 次判定；Boss 额外 `zoneBossExtraDraws(=2)` 次 | `unit.service.ts:455` / `app-config.ts:92` |
| 单位 = `realm` + `camp` + `gives_lingyun` + `base_stats` + `drop_table_ref`；隐藏词条 `effects`(JSON) 走池子挂载 | `schema.prisma:346-381` |

**结论：本作没有伤害/血量/命中，战斗是「资源换算」而不是「模拟对砍」。** 本轮沿用这个取向。

### 6.2 修订：门槛 / 判定 / 速率 / 产出 四段式

1. **门槛（threshold）**
   - 地图线路图节点：**固定值**（由节点 `level` 决定），因为「每个图的怪物等级固定」；
   - 秘境内部：`basePower + (floor−1) × powerStep`，但 `maxFloor ≤ 3`（D8），
     所以只是一个**三段式的小爬升**，不再承担 T 阶晋升；
   - Boss 层：`threshold × bossMul`（建议 1.5）。
2. **胜负判定（确定性，无随机）**
   - `playerPower ≥ threshold` → **可推进**（节点通过 / 秘境涨层）；
   - `playerPower < threshold` → **卡住**：不涨任何进度，改为「原地刷当前目标」。
   - 判定**只有两态**，不引入命中率/暴击/随机失败 —— 放置游戏的离线收益必须是确定的，
     否则玩家无法预期挂机产出（这是本作明确拒绝的 PoE 硬核面向）。
3. **碾压比 → 击杀速率（本轮的关键新增）**
   ```
   killsPerTick = clamp(round(K × (playerPower / threshold) ^ α), 1, cap)
   ```
   建议 `K = 1`、`α = 1.5`、`cap = 20`（全部可配）。
   **为什么必须有这一段**：若判定只有「过 / 不过」两态，则玩家一旦过线就再无追求，
   装备与功法立刻失去意义。有了速率，**战力溢出 = 每小时产出更高**，
   于是「继续变强」在通关之后依然有正反馈 —— 这是放置游戏的核心驱动。
4. **产出**：沿用现有实现 —— 每杀 `gives_lingyun` 时给`realmLingyun(单位境界)`，
   并按掉落表做 `dropsPerKill` 次判定（Boss 额外 2 次）。
   即：**产出 = 击杀速率 × 单杀产出**，速率由碾压比决定，单杀产出由节点等级决定。
5. **卡层时的产出**：仍给产出但打折（建议 `×0.5`，且速率取下限 1）。
   理由：让「挂错目标」有惩罚但不至于零收益 —— 玩家可以自己发现应该换地方。

### 6.3 隐藏词条的作用面（`effects` JSON 建议 schema）

确定性模型下隐藏词条**不能改伤害**（没有伤害），只能改**门槛与奖励**。建议 `effects` 定型为：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `thresholdMul` | 门槛倍率（更难打） | 「坚韧」1.15 |
| `lingyunMul` | 灵韵产出倍率（更肥） | 「灵蕴」1.5 |
| `dropDrawBonus` | 额外掉落判定次数 | 「肥硕」+1 |

设计意图：让隐藏词条形成**风险/收益取舍**（更难打但更肥），而不是无脑加难度。
`game_unit_hidden_pools` 的权重机制已实现，本轮只需**给 `effects` 定义 schema 并落 seed**。

### 6.4 明确不做

- 不做伤害 / 血量 / 暴击 / 命中 / 闪避（与确定性检定冲突）；
- 不做随机胜负；
- 不做实时手操（D1 已定：全自动实时推进）；
- 不引入「战斗中突破」（R1-1 已禁）。

## 7. R2-9 青云宗地图（地图 1 · 第 1-2 章）

### 7.1 构想来源

**逐字来源：`user-docs/青云宗地图构想.md`**（用户提供）。结构定名为

### 7.2 结构：四层同心环

| 层级 | 内容 | 数量 |
| --- | --- | --- |
| 外环 | 东门 / 南门 / 西门 / 北门（护山大阵最外环） | 4 |
| 过渡 | 外门接引区域（四方来客汇入处） | 1 |

**这比链式设计好在三点**（也是它值得作为后续地图模板的原因）：

1. **拓扑天然有分支**：四方山门四路汇入，八峰成环，玩家有真实路线选择，而不是单行道；

3. **它是「地点宿主」，不是「关卡列表」**：每个节点可以承载一个**系统**

   不必等所有系统都实现** —— 未实现的系统在图上显示为「未开放」。
