# 14 · 地图画布方案探讨（n×n 格子 + 可交互对象）

> 起因（用户，2026-09-13）：
> 「我之所以以字符画形式描述了地图，就是希望能以画布方式，或者伪画布渲染地图节点。请探讨方案：
> **大地图以 n×n 格子定义，然后地图节点就落于某个具体的格子**，这样前端可以接受后端地图定义，
> 直接使用 antd 组件去渲染。**进入地图之后，加载目标地图的可交互对象**，如 npc、传送点、秘境入口，
> 甚至是随机刷新的怪物。总体设想是，在 pc 端，**左边地图网格，右边地图内可交互对象**，
> 也就是说，**必须和传送点交互之后才可解锁传送**。」

> `13-地图面板实施任务书.md` §8（功能通过、表现层待大改）。

## 0. 一句话结论

**可行，而且比现在的「按环层分组堆按钮」强很多。** 但要先分清一件事：

> **格子是「显示层」还是「玩法层」？**

| 档位 | 含义 | 成本 | 现在的实现能不能留 |
| --- | --- | --- | --- |
| **L1 · 布局** | 格子只决定**画在哪**；移动仍是「点相邻节点即抵达」 | 小 | ✅ 拓扑/门槛/进度全不动 |
| **L2 · 棋盘** | 角色有**格位**，逐格走过去；在线时看着它走 | 中 | ✅ 加一张状态表即可 |
| **L3 · 地形** | 格子有墙/水/机关，走法本身是玩法 | 大 | ❌ 要改移动与寻路 |

**建议：先做 L1，但按 L2 的形状落字段**（多存一个「当前格」而已）。理由：

- L1 就能交付你要的「伪画布 + 左格右对象」，且**不碰任何已验证的玩法规则**（1427 个后端测试不动）；
- L2 是 L1 的**超集**：角色令牌要画在格子上，前提就是节点有格子坐标 —— 先做 L1 不浪费；
- L3 的地形/阻挡在当前玩法里没有承载（放置游戏不需要躲避），**现在做等于给不存在的玩法付费**。

## 1. 关键判断：格子是**布局维度**，不是**拓扑维度**

这是整个方案里最重要的一条，先说清楚，否则后面全歪。

**现状（`schema.prisma:430-461`）**：`game_map_nodes.requires_node_code` + `game_map_edges` 是**权威拓扑**
（谁能到谁、什么前置），`ring` / `sector` 是**语义标签**（外环/八峰/内环/主峰）。

**提议**：新增 `grid_row` / `grid_col` 作为**第三个维度 —— 纯位置**。三者分工：

| 维度 | 字段 | 权威性 | 回答 |
| --- | --- | --- | --- |
| 拓扑 | `game_map_edges` / `requires_node_code` | **权威**，决定能不能去 | 能去哪 |
| 语义 | `ring` / `sector` / `kind` / `level` / `threshold` | **权威**，决定去了干什么 | 去了干嘛 |
| 位置 | `grid_row` / `grid_col` | **派生/表现**，决定画在哪 | 长什么样 |

**为什么位置必须非权威**：

1. 现在有 **4 个山门 → 1 个接引区** 的星形拓扑（`map-edges.json`）。如果格子相邻才算连通，
   这个拓扑在几何上**根本画不出来**（一个格子不可能同时紧贴四个相距 4 格的角）；
2. 剧情卡点（`chapter`）、前置卡点（`requires_node_code`）都不是空间概念，硬塞进格子会立刻打架；
3. 反过来，位置一旦权威，「设计师改布局」就变成「改玩法」，地图迭代会变得极贵。

> **所以：格子让地图「看起来」是空间，拓扑决定它「实际」是通路。** 视觉相邻 ≠ 可通行，
> 可通行 ≠ 视觉相邻 —— 后者用**山路连线**表达（§3.4），前者靠**关卡设计尽量对齐**（§2.4 自检）。

## 2. 后端改动清单

### 2.1 `game_maps`：加两列

```prisma
model game_maps {
  // ...现有字段不动...
  grid_rows Int @default(9) @db.SmallInt   // 棋盘行数
  grid_cols Int @default(9) @db.SmallInt   // 棋盘列数
}
```

**为什么放在 map 上而不是全局常量**：D6 的三张图应该长得不一样 —— 青云宗是**九宫同心环**，
山下凡尘可以是**沿河长条（6×14）**，混沌裂隙可以是**不规则裂口**。行列数落库，
前端拿到什么画什么，**加地图不改代码**。

### 2.2 `game_map_nodes`：加两列 + 一个唯一约束

```prisma
model game_map_nodes {
  // ...现有字段不动...
  grid_row Int @db.SmallInt   // 1-based，1..grid_rows
  grid_col Int @db.SmallInt   // 1-based，1..grid_cols
  @@unique([map_id, grid_row, grid_col])   // 一格一节点，DB 层挡住重叠
}
```

唯一约束是**必须**的：重叠格子在画布上表现为两个按钮叠在一起，是那种「肉眼看不出、
但线上很丑」的错。让 DB 直接拒绝，比靠生成器自觉可靠。

### 2.3 新增 `game_map_objects`：可交互对象

这是「进入地图之后加载可交互对象」的落点。

```prisma
model game_map_objects {
  id           Int      @id @default(autoincrement())
  code         String   @unique @db.VarChar(50)
  map_id       Int
  node_code    String   @db.VarChar(50)   // 宿主地点：对象都挂在某个地点上
  kind         String   @db.VarChar(20)   // npc / waypoint / realm_entrance / resource
  name         String   @db.VarChar(50)
  action       String   @db.VarChar(20)   // 交互动作，服务端白名单：unlock_waypoint / enter_realm / talk / gather
  feature_key  String?  @db.VarChar(20)   // 交互后打开的系统（复用 FeatureGate；null = 继承节点）
  zone_code    String?  @db.VarChar(50)   // action=enter_realm 时指向 game_zones.code
  level        Int?     @db.SmallInt      // 守卫/NPC 的境界（可空）
  description  String?  @db.Text
  order_index  Int
}

model game_object_progress {           // 角色 × 对象 的一次性交互状态
  id           Int      @id @default(autoincrement())
  character_id Int
  object_id    Int
  done         Boolean  @default(false)  // 传送点点亮 / NPC 已结识 / 资源点已采
  use_count    Int      @default(0)
  updated_at   DateTime @updatedAt @db.Timestamp(6)
  @@unique([character_id, object_id])
}
```

**对象为什么挂在 `node_code` 而不是自己带坐标**：一个「地点」就是一个场景，
NPC/传送点/秘境入口都**立在这块地上**。给对象单独配坐标会立刻引出「对象和节点互相错位」
「多个对象抢同一格」的麻烦，而收益为零 —— 右侧面板是列表，不需要空间位置。

> 例外：如果之后要做 **L2（角色逐格走）** 且希望怪物站在格子中间，再给对象加
> **可空**的 `grid_row` / `grid_col`（缺省继承宿主节点格）。这是加法，不是改法。

### 2.4 种子生成器：落格算法 + 自检

`packages/server/scripts/gen-map-seed.mjs` 已经在做「生成 3 个种子 + 自检」，这里**加两步**：

**落格算法（确定性，不用力导向）** —— 已用探针验证（§9）：

1. **锚定**：有 `sector` 的节点直接算 —— `ring → 半径`、`sector → 方位角`，
   `(row, col) = 中心 + 方位向量 × 半径`。于是八峰自动落在**八方位**、四门自动落在**四正方位**；
2. **BFS 贪心**：没有 `sector` 的（接引区、13 个内环节点）按**拓扑 BFS**，
   每个节点挑「离父节点最近、且略偏中心」的空格；
3. **落库为显式坐标**：生成器把算出来的 `gridRow` / `gridCol` **写进种子 JSON**，
   面板不做任何布局计算 —— 想手调就直接改种子，改完自检会挡住撞格。

**自检新增项**（都必须是**硬失败**，不是警告）：

| 检查 | 为什么 |
| --- | --- |
| 坐标在 `1..grid_rows` / `1..grid_cols` 内 | 越界 = 节点画到棋盘外，用户永远点不到 |
| 同图无撞格 | DB 唯一约束的前置兜底（种子阶段就报，比 DB 报错好定位） |
| 每个节点都落了格 | 漏格 = 节点在列表里存在、在画布上消失 |
| **边的格子跨度分布** | 见下 |

**「边的格子跨度」这条要单独讲** —— 它是本方案最有价值的一个新自检项：

> 拓扑是权威的，所以**长边不会报错，只会难看**：一条跨 7 格的边在画布上会画出一条
> 横扫全图的山路，把其他节点压过去。所以自检应该**输出跨度直方图**（如 `{1:18, 2:1, 3:8}`）
> 并在 `max span > 阈值` 时**失败**，逼迫「要么挪节点，要么改拓扑」。

实测数据（§9.2）：**现在的拓扑**（四门 → 接引区）最长边跨 **7 格**；
**把四门改接本方位八峰后**最长边降到 **3 格**。这就是下面这条设计发现的量化形式。

> ### 🔎 设计发现：网格会把「枢纽节点」暴露出来
>
> 现在 `东门/南门/西门/北门 → 外门接引区` 是一个**一拖四的星形枢纽**。
> 在「按环层分组堆按钮」的旧 UI 里完全看不出来（都是平铺的按钮）；
> **放到网格上立刻变成四条横穿全图的长线**（实测跨度 5/4/7/4 格）。
>
> 三个选项（**需要你拍板**）：
>
> | 选项 | 做法 | 效果 | 代价 |
> | --- | --- | --- | --- |
> | **A · 顺拓扑** | 四门各接**本方位八峰**，接引区只留北门 | 最长边 7 → **3**，棋盘干净（§9.2） | 改 3 条边；接引区从「枢纽」降级为「北门内的落脚点」 |
> | **B · 保留枢纽** | 拓扑不动，四条长线照画 | 中心辐射状，像驿站地图 | 长线穿过八峰环，视觉噪音大 |
> | **C · 加走廊格** | 引入「路格」实体，长边沿走廊绕行 | 最像 PoE，可做迷雾 | 多一张表/一套地形语义，成本跳到 L3 |
>
> **我推荐 A**：改动最小（3 条边），效果最大，而且「从哪个门进来就先遇到哪座峰」本身
> 就比「四个门都通向同一个广场」更符合跑图直觉。

### 2.5 被删掉的两列（**单一口径**）

`has_waypoint` 与 `zone_code` 现在挂在 `game_map_nodes` 上，但按你的新设想它们其实是
**「对象」的属性**（「传送点」是一个可交互对象，「秘境入口」也是一个可交互对象）。
继续留在节点上就是**两处真相**，迟早错位。提议：

| 旧列 | 处置 | 理由 |
| --- | --- | --- |
| `game_map_nodes.has_waypoint` | **删除**，由 `objects.some(kind='waypoint')` 派生 | 「有没有传送点」= 「有没有那个对象」 |
| `game_map_nodes.zone_code` | **移到** `game_map_objects.zone_code` | 秘境入口是对象；节点只管「这是块什么地」 |

DTO 里仍然保留 `hasWaypoint` / `zoneCode` 两个**只读派生字段**（服务端算好下发），
面板改动就小得多 —— 这是「后端改结构、前端少改」的常见取法。

> ⚠️ 顺带修正一条**旧规则**：`map.service.ts:250` 现在是
> `waypointOpen = existing?.waypoint_unlocked || node.has_waypoint` —— **首次到达即自动点亮**。
> 你要的「必须和传送点交互之后才可解锁」直接推翻它。这是 `settings-revision-2.md` §5.2
> 里那句「首次到达该节点即解锁其传送点」的**改写**，需要登记成新决策（见 §5.2）。

### 2.6 需要新增「当前格位」吗？

你的「必须和传送点交互之后才可解锁」引出一个小问题：**在哪里交互？**

- **松口径**：只要 `visited` 就能交互 —— 不用新增字段，但玩家可以在东门点亮西门传送点，跑图失去意义；
- **紧口径**：**人必须在该地点**才能交互 —— 需要持久化「当前节点」。

现在 `currentCode` 只在**前端内存**里（`map-store.ts`，会话级），服务端不知道你在哪。
紧口径要加一张表（对齐现有 `game_zone_state.current_zone_id` 的写法）：

```prisma
model game_map_state {
  character_id   Int @unique
  current_node_id Int?
  updated_at     DateTime @updatedAt
}
```

**我推荐紧口径**，理由有二：

1. 它顺手给了 **L2 需要的「当前格位」** —— 一次投入，两处收益；
2. 「跑过去 → 点亮 → 下次直接飞」是跑图玩法的**全部意义**；松口径会把它降级成「点一下列表」。

代价：`map.enter` 要多写一行状态，`map.interact` 要多查一次「你在不在那」。

## 3. 前端渲染方案（伪画布）

### 3.1 先说一个**实测否决**：不能用 antd `Row`/`Col`

`@idle-path/ui-kit` 的 `SlotBoard` 用 `Row`/`Col` + 一个 `spanFor()` 把列数换算成 24 栅格占宽，
**不能整除时把余数摊给前几列**（`SlotBoard/index.tsx:48-57`，如 5 列 → 5/5/5/5/4）。

这个技巧对**一维换行列表**是对的，对**二维棋盘是致命的**：

```
9 列 → spanFor 依次给出 3,3,3,3,3,3,2,2,2
      第 1 行 9 格的宽度：3 3 3 3 3 3 2 2 2   ← 24，铺满
      第 2 行同样的序列：3 3 3 3 3 3 2 2 2
      → 第 7 列在所有行里都是 2 单位，列是「对齐」的 …… 但第 1 列是 3、第 7 列是 2
      → **列宽不等**，节点卡宽度不一致，看着像排版坏了
```

结论：**棋盘必须用真正的二维网格**（CSS Grid），不能用 24 栅格模拟。
所以「用 antd 组件渲染」应理解为：**棋盘骨架用 CSS Grid，格子里的内容全部用 antd 组件**
（`Card` / `Button` / `Badge` / `Tag` / `Tooltip` / `Typography`）。

### 3.2 棋盘骨架

```
┌─ GridCanvas（ui-kit 通用原语，零业务）───────────────────────┐
│  <div style={{ display:'grid',                              │
│                gridTemplateColumns:`repeat(${cols},1fr)`,   │
│                gridTemplateRows:`repeat(${rows},1fr)`,      │
│                aspectRatio:`${cols} / ${rows}`,             │
│                position:'relative' }}>                      │
│    <GridLinks …/>        ← 绝对定位的 SVG 连线层（在底层）    │
│    {items.map(…) }       ← 每个 item 用 gridRow/gridColumn 落格 │
│  </div>                                                     │
└─────────────────────────────────────────────────────────────┘
```

要点：

- **`aspectRatio: cols/rows`** 是关键：它保证格子是**正方形**，于是「格坐标 → 百分比坐标」
  是线性的，连线层不需要知道任何像素值，**缩放自适应**（PC 宽屏 / 手机窄屏同一套代码）；
- **不写死像素**：cell 尺寸交给容器，`minmax(0, 1fr)` 防止内容把格子撑歪；
- **颜色零 hex**：连线用 `theme.useToken()` 取 `token.colorBorder` / `token.colorPrimary`
  作为 SVG `stroke`（ui-kit 已有 11 个组件这样取色，合规）；
- 门禁友好：内联 `style` 只做布局（无 hex、无 `!important`、无 `<style>`），过
  `test/hygiene.test.ts` 红线 2/3/4。

### 3.3 ui-kit 新原语：`GridCanvas`

按「组件能抽就抽」的硬要求（`11-…手册.md` §4），棋盘骨架是**纯几何**、**零业务**的，
必须抽到 ui-kit，而不是塞进 `MapPanel`：

```
packages/ui-kit/src/layout/GridCanvas/
├── index.tsx          容器：CSS Grid + 落格 + 选中态
├── GridLinks.tsx      连线层：绝对定位 SVG（坐标由格号换算成百分比）
├── types.ts           GridItem / GridLink（纯类型）
└── *.test.tsx         各自同目录单测
```

```ts
export interface GridItem { key: string; row: number; col: number; content: ReactNode;
                            onSelect?: () => void; selected?: boolean; disabled?: boolean; title?: string }
export interface GridLink { from: string; to: string; state?: 'normal' | 'active' | 'locked' }
export interface GridCanvasProps { rows: number; cols: number; items: readonly GridItem[];
                                   links?: readonly GridLink[]; ariaLabel?: string }
```

**它为什么值得进 ui-kit**：任何「位置固定 + 有连接关系」的二维盘面都能用 ——
阵法图、天赋树、炼丹火候图、宗门地图。这不是为地图一次性造轮子。

### 3.4 山路：**派生**，不落库

你要的字符画里有 `┌──┴──┐` 这种「路」。**路不需要存**：
`GridLinks` 拿到 `edges` + 两端格号，算一条 **L 形正交路径**（先横后纵 or 先纵后横）
画出来即可。三种画法可选：

| 画法 | 说明 | 观感 |
| --- | --- | --- |
| 直线 | 两端格心直连（SVG `<line>`） | 简洁，但斜线在方格上略「漂」 |
| **L 形正交** | 先横后纵两段 | **最像你画的字符画**，推荐 |
| 圆角正交 | L 形 + 拐角 `arc` | 温润，成本略高 |

不落库的好处：**拓扑改了路自动跟着变**，不会出现「边改了路还是旧的」这种经典漂移。

- 移动端用 `Grid.useBreakpoint()` 切上下堆叠 —— **`Row`/`Col` 的响应式 span 在这里是合适的**

## 4. 「进入地图之后加载可交互对象」

### 4.1 对象类型（首批）

| `kind` | 中文 | `action` | 交互结果 | 状态字段 |
| --- | --- | --- | --- | --- |
| `waypoint` | 传送点 | `unlock_waypoint` | **点亮**，之后可 `map.waypoint` 直达 | `game_node_progress.waypoint_unlocked` |
| `realm_entrance` | 秘境入口 | `enter_realm` | 切挂机/历练目标到该 `zone_code` | `game_zone_state.current_zone_id` |
| `npc` | NPC | `talk` | 打开承载系统（`feature_key`）或剧情 | `game_object_progress.done` |
| `resource` | 资源点 | `gather` | 采集（可重复，`use_count++`） | `game_object_progress.use_count` |

**「随机刷新的怪物」我建议不进这张表**（这条是**减法建议**，见下）。

### 4.2 传送点：从「到达即点亮」改成「交互才点亮」

```ts
// 现在（map.service.ts:250）—— 到达就送
const waypointOpen = Boolean(existing?.waypoint_unlocked) || Boolean(node.has_waypoint);

// 改成
//   map.enter      → visited = TRUE，传送点对象变为「可交互」
//   map.interact   → { nodeCode, objectCode }，action='unlock_waypoint' → waypoint_unlocked = TRUE
//   map.waypoint   → 仍然要求 waypoint_unlocked（门槛没变，只是拿到的路径变长了）
```

**新增闸门**（都要有边界测试，按 `AGENTS.local.md` §4）：

| 错误码 | 触发 |
| --- | --- |
| `OBJECT_NOT_FOUND` | `objectCode` 不存在或不属于该 `nodeCode` |
| `OBJECT_NOT_AVAILABLE` | 宿主节点未发现 / 未到达（紧口径下：人不在该节点） |
| `OBJECT_ALREADY_DONE` | 一次性对象已交互（幂等应返回成功还是这个码？**待拍板**） |
| `OBJECT_ACTION_UNSUPPORTED` | `action` 不在白名单 |

> 这条规则**改写的是 §5.2**。§5.2 原文：「**首次到达**该节点即解锁其传送点」。
> 新规则：「**首次到达**使传送点变为**可交互**；**交互**后点亮」。
> 差别看着小，但它把「跑图」从一个**经过**动作变成了一个**目的**动作 ——
> 玩家在山门前必须停一下点一下，地图才真正向他打开。这是对你那句
> 「必须和传送点交互之后才可解锁传送」的忠实落地。

### 4.3 为什么我建议**不做**「随机刷怪」对象

你说的「甚至随机刷新的怪物」最自然的落点其实**已经有了**：§4.2 的在线探索 tick 模型。

- tick 模型已经定义了「在线时服务端按秒推进、按掉落表判定产出」（R2 §4.2）；
- 把「随机刷新怪物」做成**对象表里的持久实体**，就要额外解决：谁刷新、什么时候、死了多久重生、
  离线期间刷不刷（**一旦要算，就开了「离线也能兑进度」的口子，与核心循环冲突**）；
- 而做成 **tick 里的事件**（「你在此地遭遇了 3 只妖兽，已击杀」），零新增状态、
  天然在线限定时、天然不可伪造。

**所以建议**：`game_map_objects` 只放**持久可交互物**（NPC / 传送点 / 秘境入口 / 资源点）；
怪物走 tick，不进对象表。若之后确实需要「看得见的怪物站在格子上」，再给对象表加
可空坐标（§2.3 已留口）。

### 5.2 要改的（登记为新决策）

> **D15 单独说**：§5.7 的「待明确 26」（未探索节点在 UI 上是否可见）**在画布方案下必须拍板**，
> 因为它从「一个可选项」变成了「画布好不好看的前提」：
>
> - **不下发** → 棋盘上是**空洞**，玩家看到一个残缺的图形，不知道那边有没有路；
> - **下发轮廓** → 棋盘上有**虚线灰格 / 「？」**，玩家知道「那边有东西，还没去过」，
>   这就是 PoE 的未探索区域观感，**探索欲直接来自这里**。
>
> **我推荐下发轮廓**：只给 `code / gridRow / gridCol / discovered:false`，
> **名字、境界、门槛一个都不给**（不给名字才不剧透）。代价：`discoveredCodes` 的返回从
> 「过滤」改成「打标」，服务端 3 处 + DTO 1 处 + 若干测试要跟着改。
