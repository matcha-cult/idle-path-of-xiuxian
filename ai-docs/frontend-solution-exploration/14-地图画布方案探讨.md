## 0.1 一句话结论

**可行，而且比现在的「按环层分组堆按钮」强很多。** 但要先分清一件事：

> **格子是「显示层」还是「玩法层」？**

| 档位 | 含义 | 成本 | 现在的实现能不能留 |
| --- | --- | --- | --- |
| **L1 · 布局** | 格子只决定**画在哪**；移动仍是「点相邻节点即抵达」 | 小 | ✅ 拓扑/门槛/进度全不动 |
| **L2 · 棋盘** | 角色有**格位**，逐格走过去；在线时看着它走 | 中 | ✅ 加一张状态表即可 |
| **L3 · 地形** | 格子有墙/水/机关，走法本身是玩法 | 大 | ❌ 要改移动与寻路 |

**建议：先做 L1，但按 L2 的形状落字段**（多存一个「当前格」而已）。理由：

- L1 就能交付你要的「伪画布 + 左格右对象」，且**不碰任何已验证的玩法规则**（1427 个后端测试不动）；
- L2 是 L1 的**超集**：角色令牌要画在格子上，前提就是节点有格子坐标 —— 先做 L1 不浪费；
- L3 的地形/阻挡在当前玩法里没有承载（放置游戏不需要躲避），**现在做等于给不存在的玩法付费**。

## 1. 关键判断：格子是**布局维度**，不是**拓扑维度**

这是整个方案里最重要的一条，先说清楚，否则后面全歪。

**现状（`schema.prisma:430-461`）**：`game_map_nodes.requires_node_code` + `game_map_edges` 是**权威拓扑**
（谁能到谁、什么前置），`ring` / `sector` 是**语义标签**（外环/八峰/内环/主峰）。

**提议**：新增 `grid_row` / `grid_col` 作为**第三个维度 —— 纯位置**。三者分工：

| 维度 | 字段 | 权威性 | 回答 |
| --- | --- | --- | --- |
| 拓扑 | `game_map_edges` / `requires_node_code` | **权威**，决定能不能去 | 能去哪 |
| 语义 | `ring` / `sector` / `kind` / `level` / `threshold` | **权威**，决定去了干什么 | 去了干嘛 |
| 位置 | `grid_row` / `grid_col` | **派生/表现**，决定画在哪 | 长什么样 |

**并且：位置只在后端与换算里存在，前端不把它画出来**（C1）。`grid_row/col` 的唯一用途是
**换算成百分比坐标**：

```
x% = (grid_col - 0.5) / grid_cols × 100
y% = (grid_row - 0.5) / grid_rows × 100
```

于是「9×9」对玩家而言只是「这张图上枢纽排成 9 行 9 列的那个疏密」，
屏幕上**没有任何一条网格线**。

**为什么位置必须非权威**：

1. 现在有 **4 个山门 → 1 个接引区** 的星形拓扑（`map-edges.json`）。如果格子相邻才算连通，
   这个拓扑在几何上**根本画不出来**（一个格子不可能同时紧贴四个相距 4 格的角）；
2. 剧情卡点（`chapter`）、前置卡点（`requires_node_code`）都不是空间概念，硬塞进格子会立刻打架；
3. 反过来，位置一旦权威，「设计师改布局」就变成「改玩法」，地图迭代会变得极贵。

> **所以：坐标让地图「看起来」是空间，拓扑决定它「实际」是通路。** 视觉相邻 ≠ 可通行，
> 可通行 ≠ 视觉相邻 —— 后者用**连线**表达（§3.5），前者靠**关卡设计尽量对齐**（§2.4 自检）。

## 2. 后端改动清单

### 2.1 `game_maps`：加两列坐标 + 预留底图

```prisma
model game_maps {
  // ...现有字段不动...
  grid_rows      Int     @default(9) @db.SmallInt   // 棋盘行数（后端坐标空间，前端不画）
  grid_cols      Int     @default(9) @db.SmallInt   // 棋盘列数
  background_key String? @db.VarChar(100)           // 预留：地图底图（见 §3.6，本轮不填）
}
```

**为什么放在 map 上而不是全局常量**：D6 的三张图应该长得不一样 —— 青云宗是**九宫同心环**，
山下凡尘可以是**沿河长条（6×14）**，混沌裂隙可以是**不规则裂口**。行列数落库，
前端拿到什么画什么，**加地图不改代码**。

**`background_key` 为什么是 key 不是 url**：DB 里存 URL 会绕过打包与版本管理，
换 CDN / 换域名 / 换文件名时要么改库要么断图。存 key、由前端注册表解析成资源路径，
与本仓 `feature-registry.ts` / `panel-registry` 的既有做法一致。**本轮只加字段不填值**
（`null` = 不画底图），后期有图了只需填 key + 放文件。

### 2.2 `game_map_nodes`：加三列 + 一个唯一约束

```prisma
model game_map_nodes {
  // ...现有字段不动...
  grid_row    Int     @db.SmallInt   // 1-based，1..grid_rows
  grid_col    Int     @db.SmallInt   // 1-based，1..grid_cols
  description String? @db.Text       // 风味文案（§11.1 第 5 条：PoE 悬停卡里有）
  @@unique([map_id, grid_row, grid_col])   // 一格一节点，DB 层挡住重叠
}
```

唯一约束是**必须**的：重叠格子在画布上表现为两个按钮叠在一起，是那种「肉眼看不出、
但线上很丑」的错。让 DB 直接拒绝，比靠生成器自觉可靠。

### 2.3 新增 `game_map_objects`：可交互对象

这是「进入地图之后加载可交互对象」的落点。

```prisma
model game_map_objects {
  id           Int      @id @default(autoincrement())
  code         String   @unique @db.VarChar(50)
  map_id       Int
  node_code    String   @db.VarChar(50)   // 宿主地点：对象都挂在某个地点上
  kind         String   @db.VarChar(20)   // npc / waypoint / realm_entrance / resource
  name         String   @db.VarChar(50)
  action       String   @db.VarChar(20)   // 交互动作，服务端白名单：unlock_waypoint / enter_realm / talk / gather
  feature_key  String?  @db.VarChar(20)   // 交互后打开的系统（复用 FeatureGate；null = 继承节点）
  zone_code    String?  @db.VarChar(50)   // action=enter_realm 时指向 game_zones.code
  level        Int?     @db.SmallInt      // 守卫/NPC 的境界（可空）
  description  String?  @db.Text
  order_index  Int
}

model game_object_progress {           // 角色 × 对象 的一次性交互状态
  id           Int      @id @default(autoincrement())
  character_id Int
  object_id    Int
  done         Boolean  @default(false)  // 传送点点亮 / NPC 已结识 / 资源点已采
  use_count    Int      @default(0)
  updated_at   DateTime @updatedAt @db.Timestamp(6)
  @@unique([character_id, object_id])
}
```

**对象为什么挂在 `node_code` 而不是自己带坐标**：一个「地点」就是一个场景，
NPC/传送点/秘境入口都**立在这块地上**。给对象单独配坐标会立刻引出「对象和节点互相错位」
「多个对象抢同一格」的麻烦，而收益为零 —— 右侧面板是列表，不需要空间位置。

> 例外：如果之后要做 **L2（角色逐格走）** 且希望怪物站在格子中间，再给对象加
> **可空**的 `grid_row` / `grid_col`（缺省继承宿主节点格）。这是加法，不是改法。

### 2.4 种子生成器：落格算法 + 自检

`packages/server/scripts/gen-map-seed.mjs` 已经在做「生成 3 个种子 + 自检」，这里**加两步**：

**落格算法（确定性，不用力导向）** —— 已用探针验证（§9）：

1. **锚定**：有 `sector` 的节点直接算 —— `ring → 半径`、`sector → 方位角`，
   `(row, col) = 中心 + 方位向量 × 半径`。于是八峰自动落在**八方位**、四门自动落在**四正方位**；
2. **BFS 贪心**：没有 `sector` 的（接引区、13 个内环节点）按**拓扑 BFS**，
   每个节点挑「离父节点最近、且略偏中心」的空格；
3. **落库为显式坐标**：生成器把算出来的 `gridRow` / `gridCol` **写进种子 JSON**，
   面板不做任何布局计算 —— 想手调就直接改种子，改完自检会挡住撞格。

**自检新增项** —— 分**硬失败**（挡住提交）与**软警告**（只打印，供人判断）两类：

| 检查 | 级别 | 为什么 |
| --- | --- | --- |
| 坐标在 `1..grid_rows` / `1..grid_cols` 内 | **硬** | 越界 = 枢纽画到画布外，用户永远点不到 |
| 同图无撞格 | **硬** | DB 唯一约束的前置兜底（种子阶段就报，比 DB 报错好定位） |
| 每个节点都落了格 | **硬** | 漏格 = 节点在列表里存在、在画布上消失 |
| **连线交叉数** | **硬**（阈值） | 交叉是画布上最刺眼的瑕疵，没有「合理的长线」这种解释 |
| **边的几何跨度分布** | **软**（只打印） | PoE 自己就有横穿全图的长线（§11.3）—— 长不等于丑，交给人判断 |
| **落点最大偏移**（实际格 vs 极坐标理想位） | **硬**（≤ ~2 格） | 见 §11.4：`sep` 贪大就会把节点推离理想环，这条是「环形还美不美」的真判据 |
| **不相邻枢纽最小间距** | **软**（只打印） | 只统计**不相邻**的：相邻枢纽本就该挨着（§11.4 附注） |

**「边的几何跨度」这条要单独讲** —— 它是本方案最有价值的一个新自检项：

> 拓扑是权威的，所以**长边不会报错，只会难看** —— 但「多长算难看」这件事，
> **PoE 已经给了答案**：它的剧情图上就有横穿全图的连线（通往「快捷传送点」那条），
> 而它读起来完全不刺眼，因为线**细、淡、无箭头**（§11.1 第 3 条）。
>
> 所以两个指标要**分开对待**：
>
> - **跨度直方图**（如 `{1:18, 2:1, 3:8}`）与最大跨度 → **只打印，不失败**。
>   它是一份「关卡设计体检报告」，供人判断要不要挪节点；
> - **连线交叉数**（两两线段求交，排除共享端点）→ **建议硬卡阈值**。
>   交叉没有任何「合理」的解释，是纯粹的观感 bug。
>
> 这一条在「格子不可见」之后更值得做：没有网格线做参照，连线一旦乱，满屏都是斜杠。

实测数据（§9.2）：**现在的拓扑**（四门 → 接引区）最长边跨 **7 格**；
**把四门改接本方位八峰后**最长边降到 **3 格**。这就是下面这条设计发现的量化形式。

> ### 🔎 设计发现：网格会把「枢纽节点」暴露出来
>
> 现在 `东门/南门/西门/北门 → 外门接引区` 是一个**一拖四的星形枢纽**。
> 在「按环层分组堆按钮」的旧 UI 里完全看不出来（都是平铺的按钮）；
> **放到网格上立刻变成四条横穿全图的长线**（实测跨度 5/4/7/4 格）。
>
> 三个选项（**需要你拍板**）：
>
> | 选项 | 做法 | 效果 | 代价 |
> | --- | --- | --- | --- |
> | **A · 顺拓扑** | 四门各接**本方位八峰**，接引区只留北门 | 最长边 7 → **3**，画布干净（§9.2） | 改 3 条边；接引区从「枢纽」降级为「北门内的落脚点」 |
> | **B · 保留枢纽** | 拓扑不动，四条长线照画 | 中心辐射状，像驿站地图 | 长边穿过八峰环，视觉噪音大 |
> | **C · 边存控制点** | 拓扑不动；`game_map_edges` 加**可空控制点**，连线画成弯折的「山道」 | 最像 PoE（PoE 的连线就是手绘曲线） | 加 2~4 列 + 前端曲线渲染，但**仍属 L1**，不引入地形 |
>
> **我推荐 A**：改动最小（3 条边），效果最大，而且「从哪个门进来就先遇到哪座峰」本身
> 就比「四个门都通向同一个广场」更符合跑图直觉。C 是 A 的**备选**而非替代 ——
> 如果以后底图上的路是弯的，控制点就是让连线贴合底图的手段（§3.6）。

### 2.5 被删掉的两列（**单一口径**）

`has_waypoint` 与 `zone_code` 现在挂在 `game_map_nodes` 上，但按你的新设想它们其实是
**「对象」的属性**（「传送点」是一个可交互对象，「秘境入口」也是一个可交互对象）。
继续留在节点上就是**两处真相**，迟早错位。提议：

| 旧列 | 处置 | 理由 |
| --- | --- | --- |
| `game_map_nodes.has_waypoint` | **删除**，由 `objects.some(kind='waypoint')` 派生 | 「有没有传送点」= 「有没有那个对象」 |
| `game_map_nodes.zone_code` | **移到** `game_map_objects.zone_code` | 秘境入口是对象；节点只管「这是块什么地」 |

DTO 里仍然保留 `hasWaypoint` / `zoneCode` 两个**只读派生字段**（服务端算好下发），
面板改动就小得多 —— 这是「后端改结构、前端少改」的常见取法。

> ⚠️ 顺带修正一条**旧规则**：`map.service.ts:250` 现在是
> `waypointOpen = existing?.waypoint_unlocked || node.has_waypoint` —— **首次到达即自动点亮**。
> 你要的「必须和传送点交互之后才可解锁」直接推翻它。这是 `settings-revision-2.md` §5.2
> 里那句「首次到达该节点即解锁其传送点」的**改写**，需要登记成新决策（见 §5.2）。

### 2.6 需要新增「当前格位」吗？

你的「必须和传送点交互之后才可解锁」引出一个小问题：**在哪里交互？**

- **松口径**：只要 `visited` 就能交互 —— 不用新增字段，但玩家可以在东门点亮西门传送点，跑图失去意义；
- **紧口径**：**人必须在该地点**才能交互 —— 需要持久化「当前节点」。

现在 `currentCode` 只在**前端内存**里（`map-store.ts`，会话级），服务端不知道你在哪。
紧口径要加一张表（对齐现有 `game_zone_state.current_zone_id` 的写法）：

```prisma
model game_map_state {
  character_id   Int @unique
  current_node_id Int?
  updated_at     DateTime @updatedAt
}
```

**我推荐紧口径**，理由有二：

1. 它顺手给了 **L2 需要的「当前格位」** —— 一次投入，两处收益；
2. 「跑过去 → 点亮 → 下次直接飞」是跑图玩法的**全部意义**；松口径会把它降级成「点一下列表」。

代价：`map.enter` 要多写一行状态，`map.interact` 要多查一次「你在不在那」。

## 3. 前端渲染方案（**连线画布**，不是棋盘）

### 3.1 观感目标

参照 PoE 世界地图：**深色底（后期换底图）+ 若干枢纽图标 + 枢纽之间的连线**。
屏幕上**看不到任何格子**（C1）—— 棋盘只活在后端字段与一次百分比换算里。

```
        ┌──────────────┐
        │    北门 🔮    │            ← 枢纽 = antd 组件（Card/Button + Badge/Tag）
        └──────┬───────┘
               │                    ← 连线 = SVG，两端枢纽中心的直连/微弧
        ┌──────┴───────┐
        │   天枢峰      │
        └──┬────────┬──┘
           │        ╲
   ┌───────┴──┐   ┌──╲───────┐
   │  瑶光峰   │   │  天玑峰   │
   └──────────┘   └──────────┘
        （底图 `background_key` 预留：先不画，后期直接把图铺在连线层下面）
```

观感对齐用 mock：**`tmp/map-canvas-mock.html`**（纯静态 HTML，双击可开；
生成命令 `node tmp/map-grid-probe.mjs 9 --rewire --svg`；**属对齐草图，不入库**）。

### 3.2 实测否决：不能用 antd `Row`/`Col` 当坐标层

`@idle-path/ui-kit` 的 `SlotBoard` 用 `Row`/`Col` + 一个 `spanFor()` 把列数换算成 24 栅格占宽，
**不能整除时把余数摊给前几列**（`SlotBoard/index.tsx:48-57`）：

```
9 列 → spanFor 依次给出 3,3,3,3,3,3,2,2,2（和恰为 24，每行都铺满）
       → 列是对齐的，但**列宽不等**：前 6 列 3 单位、后 3 列 2 单位
       → 落在这 9 列上的枢纽，横向间距不一致，看着就是排版坏了
```

一维换行列表用这招没问题，**二维坐标定位用它是错的**。
下面给出的方案**干脆连网格布局都不用** —— 因为格子本来就不可见，
用 `grid-area` 落格反而会把「点」变成「格」（枢纽会撑满整格，而不是一个图标）。

### 3.3 骨架：一个「坐标空间」+ 两层绝对定位

```
<GraphCanvas rows={9} cols={9} items={…} links={…} backgroundKey={null|string}>
  <div style={{ position:'relative', aspectRatio: `${cols} / ${rows}`, width:'100%' }}>
    ├─ 底图层（预留）  backgroundKey 为 null → 不渲染任何东西
    ├─ 连线层  <svg viewBox={`0 0 ${cols} ${rows}`} preserveAspectRatio="none"
    │                style={{ position:'absolute', inset:0, pointerEvents:'none' }}>
    │             <line x1={colA-0.5} y1={rowA-0.5} x2={colB-0.5} y2={rowB-0.5}
    │                   vector-effect="non-scaling-stroke" stroke={token.colorBorder}/>
    └─ 枢纽层  每个 item：
                <div style={{ position:'absolute',
                              left:`${((col-0.5)/cols)*100}%`,
                              top:`${((row-0.5)/rows)*100}%`,
                              transform:'translate(-50%, -50%)' }}>
                  {antd 组件}
                </div>
```

四个关键取舍：

1. **`translate(-50%,-50%)` 居中**：枢纽是地图上的一个**点**（图标骑在坐标上），
   不是一格（格子不可见，撑满格没有意义）。这直接决定了不能用 `grid-area`；
2. **SVG 的 `viewBox` 就用格号**（`0 0 cols rows`）：两端坐标是 `col-0.5 / row-0.5`，
   **零换算**，也不需要 `ResizeObserver` 量像素；配 `preserveAspectRatio="none"`
   让 SVG 与容器同步拉伸；`vector-effect="non-scaling-stroke"` 保证**线宽不被拉伸变形**；
3. **`aspectRatio = cols/rows` 只是缺省**：格子不可见 ⇒ 格子是不是正方形**无关紧要**，
   坐标只是归一化位置。**一旦有底图，容器就改用底图的自然比例，坐标随之一并拉伸** ——
   所以底图不需要额外的比例字段，画师按 `cols:rows` 的构图习惯作画即可。
   这也是「后期底图 + 棋盘网格增强」能平滑接入的原因；
4. **颜色零 hex**：`stroke` / 边框色一律来自 `theme.useToken()`（ui-kit 已有 11 个组件这样取色）；
   内联 `style` 只做布局（无 hex、无 `!important`、无 `<style>`），过 `test/hygiene.test.ts` 红线 2/3/4。

### 3.4 ui-kit 新原语：`GraphCanvas`

按「组件能抽就抽」的硬要求（`11-…手册.md` §4），这套「归一化坐标 + 连线」的骨架是
**纯几何、零业务**的，必须抽到 ui-kit，不能塞进 `MapPanel`：

```
packages/ui-kit/src/layout/GraphCanvas/
├── index.tsx          容器：坐标空间 + 枢纽层 + 选中态 + 底图位
├── GraphLinks.tsx     连线层：SVG（坐标即格号，线宽非缩放）
├── types.ts           GraphCanvasItem / GraphCanvasLink（纯类型）
└── *.test.tsx         各自同目录单测
```

```ts
/** 归一化坐标：`col === 1` 表示最左列的中心，`col === cols` 表示最右列的中心。 */
export interface GraphCanvasItem {
  key: string; row: number; col: number; content: ReactNode;
  onSelect?: () => void; selected?: boolean; disabled?: boolean;
  /** 无障碍与悬停文案；⚠️ **不渲染到画布上**（§11.1 第 2 条：图上不写名字） */
  title?: string;
}
export interface GraphCanvasLink { from: string; to: string; state?: 'normal' | 'active' | 'locked' }
export interface GraphCanvasProps {
  rows: number; cols: number;
  items: readonly GraphCanvasItem[];
  links?: readonly GraphCanvasLink[];
  /** 预留：底图 key；null/缺省 = 不渲染底图（本轮恒为 null） */
  backgroundKey?: string | null;
  ariaLabel?: string;
}
```

**它为什么值得进 ui-kit**：任何「位置固定 + 有连接关系」的盘面都能用 ——
阵法图、天赋树、宗门关系图、炼丹火候图。这不是为地图一次性造轮子。

**边界（必须单测）**：`rows/cols ≤ 0`、`items` 空、
坐标越界（`row > rows`）、`links` 指向不存在的 `key`、重复 `key`、`links=[]`、单点无边。

### 3.5 连线：**派生**，不落库

**线不存库**：`GraphLinks` 拿 `edges` + 两端格号直接画。好处是**拓扑改了线自动跟着变**，
不会出现「边改了线还是旧的」这种经典漂移。

| 画法 | 说明 | 建议 |
| --- | --- | --- |
| **直线** | 两端中心直连 | ✅ **先做这个**，一行 `<line>` |
| 微弧 | 直线中点沿法线偏移固定的 ~8%，画二次贝塞尔 | 更像 PoE 的手绘弧线，观感更好；参数固定，仍不需落库 |
| 控制点弧 | `game_map_edges` 存控制点，让线贴合底图上的路 | ⏳ §2.4 的选项 C，有底图之后再说 |

**有底图之后连线可能是多余的**（底图上已经画了路），所以 `GraphCanvas` 需要
一个「显示连线」开关（前端状态即可，不必落库）—— 这样底图上线和图上线的两种审美都能试。

### 3.6 底图与资源落地（C3，本轮只预留）

`background_key` 要能解析成真实图片，需要定一条**资源通道**。现状：本仓
**没有任何静态资源目录**（`packages/web/` 下没有 `public/`，也没有 `.png/.svg` 引用），
所以这是个新问题，得顺手定掉：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **Web `public/` + 前端注册表**（推荐） | 建 `packages/web/public/maps/`；`backgroundKey` 经 `map-background-registry.ts` 解析为 `/maps/<key>.webp` | Vite 的 `publicDir` 默认就是 `public/`，**零配置**；dev 与 build 行为一致；key 不进 DB 的 URL 形态 |
| 服务端静态中间件 | server 暴露 `/static` | 要新配中间件；且本仓 server 目前不托管静态资源 |
| DB 存 URL / CDN | `background_url` | ❌ 换域名/换 CDN 就得改库；且绕过打包版本管理 |

**本轮动作**：只加 `background_key` 字段（恒为 `null`）+ 在 `GraphCanvas` 留 `backgroundKey` 参数，
**不建目录、不放图**。等有图了：放文件 → 填 key → 前端注册表登记，三步，不动结构。

## 4. 「进入地图之后加载可交互对象」

### 4.1 对象类型（首批）

| `kind` | 中文 | `action` | 交互结果 | 状态字段 |
| --- | --- | --- | --- | --- |
| `waypoint` | 传送点 | `unlock_waypoint` | **点亮**，之后可 `map.waypoint` 直达 | `game_node_progress.waypoint_unlocked` |
| `realm_entrance` | 秘境入口 | `enter_realm` | 切挂机/历练目标到该 `zone_code` | `game_zone_state.current_zone_id` |
| `npc` | NPC | `talk` | 打开承载系统（`feature_key`）或剧情 | `game_object_progress.done` |
| `resource` | 资源点 | `gather` | 采集（可重复，`use_count++`） | `game_object_progress.use_count` |

**「随机刷新的怪物」我建议不进这张表**（这条是**减法建议**，见下）。

### 4.2 传送点：从「到达即点亮」改成「交互才点亮」

```ts
// 现在（map.service.ts:250）—— 到达就送
const waypointOpen = Boolean(existing?.waypoint_unlocked) || Boolean(node.has_waypoint);

// 改成
//   map.enter      → visited = TRUE，传送点对象变为「可交互」
//   map.interact   → { nodeCode, objectCode }，action='unlock_waypoint' → waypoint_unlocked = TRUE
//   map.waypoint   → 仍然要求 waypoint_unlocked（门槛没变，只是拿到的路径变长了）
```

**新增闸门**（都要有边界测试，按 `AGENTS.local.md` §4）：

| 错误码 | 触发 |
| --- | --- |
| `OBJECT_NOT_FOUND` | `objectCode` 不存在或不属于该 `nodeCode` |
| `OBJECT_NOT_AVAILABLE` | 宿主节点未发现 / 未到达（紧口径下：人不在该节点） |
| `OBJECT_ALREADY_DONE` | 一次性对象已交互（幂等应返回成功还是这个码？**待拍板**） |
| `OBJECT_ACTION_UNSUPPORTED` | `action` 不在白名单 |

> 这条规则**改写的是 §5.2**。§5.2 原文：「**首次到达**该节点即解锁其传送点」。
> 新规则：「**首次到达**使传送点变为**可交互**；**交互**后点亮」。
> 差别看着小，但它把「跑图」从一个**经过**动作变成了一个**目的**动作 ——
> 玩家在山门前必须停一下点一下，地图才真正向他打开。这是对你那句
> 「必须和传送点交互之后才可解锁传送」的忠实落地。

### 4.3 为什么我建议**不做**「随机刷怪」对象

你说的「甚至随机刷新的怪物」最自然的落点其实**已经有了**：§4.2 的在线探索 tick 模型。

- tick 模型已经定义了「在线时服务端按秒推进、按掉落表判定产出」（R2 §4.2）；
- 把「随机刷新怪物」做成**对象表里的持久实体**，就要额外解决：谁刷新、什么时候、死了多久重生、
  离线期间刷不刷（**一旦要算，就开了「离线也能兑进度」的口子，与核心循环冲突**）；
- 而做成 **tick 里的事件**（「你在此地遭遇了 3 只妖兽，已击杀」），零新增状态、
  天然在线限定时、天然不可伪造。

**所以建议**：`game_map_objects` 只放**持久可交互物**（NPC / 传送点 / 秘境入口 / 资源点）；
怪物走 tick，不进对象表。若之后确实需要「看得见的怪物站在格子上」，再给对象表加
可空坐标（§2.3 已留口）。

### 5.1 不动的

### 5.2 要改的（登记为新决策）

| # | 议题 | 旧 | 新 | 影响面 |
| --- | --- | --- | --- | --- |
| **D12** | 传送点解锁 | 首次到达**即**点亮（§5.2） | 首次到达**使可交互**，**交互后**点亮 | `map.service.enter` / 新 `map.interact` / §5.2 正文 |
| **D13** | 地图空间表示 | 无（仅 `ring`/`sector` 语义） | **n×n 格子为布局维度**，拓扑仍权威 | 4 张表 + 生成器 + 面板 |
| **D14** | 可交互对象 | 无 | 新增对象层（NPC/传送点/秘境入口/资源点） | 新表 ×2 + `map.interact` |
| **D15** | 未发现节点是否下发 | **不下发**（§5.2「未解锁显示为未探索」但无数据） | **下发轮廓**：`discovered:false`，`name/level/threshold` 全为 null | DTO + `discoveredCodes` + 面板 |

> **D15 单独说**：§5.7 的「待明确 26」（未探索节点在 UI 上是否可见）**在画布方案下必须拍板**，
> 因为它从「一个可选项」变成了「画布好不好看的前提」：
>
> - **不下发** → 画布上是**断头路**：枢纽缺席，它的所有连线也跟着消失，玩家看到的是一张
>   残图，而且分不清「那边没东西」和「那边还没去过」；
> - **下发轮廓** → 画布上有**虚线灰点 / 「？」**，玩家知道「那边有东西，还没去过」，
>   这就是 PoE 的未探索区域观感，**探索欲直接来自这里**。
>
> **我推荐下发轮廓**：只给 `code / gridRow / gridCol / discovered:false`，
> **名字、境界、门槛一个都不给**（不给名字才不剧透）。代价：`discoveredCodes` 的返回从
> 「过滤」改成「打标」，服务端 3 处 + DTO 1 处 + 若干测试要跟着改。
>
> 附带一条：**连线是否也下发**？未到达枢纽的连线若下发，玩家能看出「那团灰点是有路的」；
> 若不下发，灰点就是孤立点。建议**连线跟随节点**（两端都下发才下发），
> 让「已揭开的区域」自然连成片 —— 这本身就是迷雾效果。

### 11.4 实测订正：**密集格子完全能排出美观的环形**（我上一版判断错了）

我上一版写「画布固定时 n 越大每格像素越小，枢纽反而更挤，所以 9×9 是上限」。
**那是错的 —— 它测的是我的生成器规则的缺陷，不是格子的限制。** 两个规则错误：

1. **BFS 贪婪挑「离父节点最近」的格** → 子节点永远贴父节点 1 格 →
   于是「每格像素变小」直接变成「枢纽变挤」。正确做法是**极坐标初值按 n 成比例**
   （`ring → 半径`、`sector/layer → 角度`），不依赖「贴父节点」。
2. **对全部节点强制最小间距 `sep`** → 把「四门紧贴八峰」判成冲突，门被挤到棋盘角上。
   正确做法是**拓扑相邻的枢纽允许贴近**（它们之间本来就要画连线），只有不相邻的才要求 `sep`。

改正后（`tmp/map-layout.mjs`）的实测，**两个指标一起看**（画布短边 660px）：

| n | sep | 不相邻枢纽最小间距 | 落点**最大偏移** | 八峰半径 σ | 评价 |
| --- | --- | --- | --- | --- | --- |
| 9 | 1 | 73.3px | 1.41 格 | 0.09 | ✅ 贴合理想环 |
| 9 | 2 | 146.7px | **8.94 格** | 0.09 | ❌ 内环节点被甩到棋盘角上 |
| 13 | 2 | 101.5px | 2.69 格 | 0.33 | ⚠️ 环稍走样 |
| 15 | 2 | 88.0px | 2.44 格 | 0.17 | ⚠️ |
| **17** | **2** | **77.6px** | **2.00 格** | **0.04** | ✅ **最佳平衡：环最圆、间距够、偏移小** |
| 17 | 3 | 116.5px | **7.07 格** | 0.04 | ❌ 强行拉间距，形状崩 |
| 21 | 2 | 62.9px | 2.00 格 | 0.26 | ⚠️ |

**三条结论**：

1. **密集格子排美观环形完全可行** —— n=17/sep=2 的八峰半径标准差只有 **0.04 格**（几乎是完美圆环），
   落点最大偏移仅 2 格。**你说得对，我上一版的结论作废。**
2. **拥挤度由 `sep` 决定，不由 n 决定** —— 「n 越大越挤」这个因果关系根本不存在。
3. **但 `sep` 不能贪**：`sep` 一大，落点就被推离理想位（n=9 强上 `sep=2` → 最大偏移 **8.94 格**，
   内环节点被甩到棋盘四个角）。**判据是 `落点最大偏移 ≤ ~2 格`，不是「间距越大越好」。**

**所以选 n 的正确问法是**：「在落点最大偏移 ≤ 2 格的前提下，谁的最小间距最大？」
→ 答：**n=17 / sep=2（77.6px）**。这就是把推荐从 9×9 改成 **17×17** 的理由。

> 附注：`minGapPx` **只统计不相邻的枢纽** —— 相邻枢纽本来就该挨着，
> 把它们算进「拥挤度」是错的（第一版就是这么错的）。

**移动端判据也随之改写**：不是「n ≤ 9」，而是

> 生成器还有一个旋钮 **`arc`（内环每节点占多少格弧长，建议 2.8）**：
> 弧长恒定 ⇒ 半径越小张角越大 ⇒ 外层贴着西门、内层自然绕成环。
> `arc=2.8 / sep=2 / n=17` 是扫描后「满足最大偏移 ≤ 2 格且间距最大」的解。

**用户拍板取 21×21。** 补测（画布短边 530px，即 §11.7 的 mock 尺寸）：

| n / sep | 不相邻最小间距 | 最大偏移 | 八峰 σ | |
| --- | --- | --- | --- | --- |
| 17 / 2 | 62.4px | 2.00 格 | 0.04 | 更宽松、更圆 |
| **21 / 2** | **50.5px** | **2.00 格** | 0.26 | ✅ **用户选定**：落点更自由 |
| 21 / 3 | 75.7px | 5.00 格 | 0.26 | ❌ 形状崩 |

> **代价要记住**：同样 `sep=2` 下，n 越大每格像素越小 ⇒ **21 的最小间距比 17 小约 20%**。
> 因此 21×21 对**画布尺寸**的要求更高：按 `(画布短边 / n) × sep ≥ 图标 + 8px`
> （图标 34px）⇒ **画布短边需 ≥ ~630px**。PC 面板高度通常够；**手机必然不够 → 横向滚动 + 列表视图**。
>
> 另：八峰 σ 从 0.04 升到 0.26 不是退步 —— 格子上 8 个点只能构成**正八边形**，
> 对角方向天然比正方向离中心近一点（n=21 时对角半径 8.49 vs 正方向 9）。这是格子的本性，不是 bug。

> **`(画布短边 / n) × sep ≥ 图标直径 + 8px`**
>
> 取 n=17 / sep=2 / 图标 34px ⇒ 每格需 ≥ 21px ⇒ **画布短边 ≥ 357px**。
> 375px 手机上刚好卡在临界，所以画布仍需**横向滚动**兜底 + 保留列表视图。

## 12. 交互契约与误触防护（用户提出）

> 用户：「交互可能需要注意，**鼠标单击就传送，可能会在移动端的时候误触**
> （因为玩家可能只是想知道这个点有啥），你需要考虑好兼容性。」

### 12.1 结论：**点击永远只「选中」，不「前往」**

| 动作 | PC | 移动端 | 结果 |
| --- | --- | --- | --- |
| 点击 / 轻点枢纽 | ✅ | ✅ | **只选中** —— 右栏显示详情 + 可交互对象 |
| 右栏「前往此地」按钮 | ✅ | ✅ | **移动（唯一的规范路径）** |
| 双击枢纽 | ✅ | ❌ | PC 快捷移动 |
| 悬停枢纽 | ✅ | — | 轻量 Tooltip（名字 + 境界） |

**三条理由**：

1. 你要的形态本来就是「左画布 + **右可交互对象**」—— 右栏既然是**动作面**，移动就该是右栏里的一个按钮；
2. 一条规则同时解决 PC 误点和移动端误触，不需要分平台写两套判定；
3. 它与「**必须和传送点交互才解锁传送**」是**同一个原则**：
   *有代价的动作，必须由明确的意图触发*。

### 12.2 移动端专项

| 问题 | 处置 |
| --- | --- |
| 图标 34px < 推荐点击尺寸 | **热区 ≥ 44×44px**：用透明扩展热区，**不改视觉尺寸** |
| 横向滚动会误触选中 | pointer 位移 > **8px 视为滚动**，不触发选中（移动端必做） |
| 触屏没有 hover | 统一「轻点 = 选中 → 右栏 / **底部 `Drawer`** 显示详情」 |
| 窄屏右栏挤压画布 | `<md` 时右栏降级为**底部抽屉**，画布占满宽度 |
| 画布太小（§11.4） | 画布保底尺寸 + **横向滚动**；并**始终保留列表视图**切换 |

### 12.3 底部提示条文案分平台

- PC：`点击枢纽查看详情 · 双击前往 · 须在枢纽处与传送点交互方可点亮`
- 移动端：`轻点枢纽查看详情 · 点「前往」移动 · 须在枢纽处与传送点交互方可点亮`

> 提示条不是装饰：**「点击只选中」这条规则是反直觉的**（PoE 里点地图节点是有动作的），
> 必须有一条常驻文案教它，否则玩家会以为点不动 = 坏了。

## 13. 开发者网格模式（用户提出）

> 用户：「在**开发者模式**的时候，先渲染出网格，**正式服就不渲染**，
> 这样能方便的给你调整建议。」

### 13.1 开关：纯前端，协议与后端零参与

```ts
// packages/web/src/pages/game/panels/map/debug-flags.ts（纯函数，可单测）
export function resolveMapDebug(
  env: { DEV?: boolean },
  search: string,
): { showGrid: boolean } {
  const p = new URLSearchParams(search).get('mapGrid');   // '1' | '0'
  if (p === '1') return { showGrid: true };
  if (p === '0') return { showGrid: false };
  return { showGrid: Boolean(env.DEV) };                  // 开发构建默认开，正式构建默认关
}
```

- **优先级：URL 参数 > 构建模式**；
- 开发构建（`pnpm dev`）**默认显示网格**；正式构建**默认不显示**；
- 正式服也能临时开：URL 加 **`?mapGrid=1`** —— 你在正式环境排查也能看到网格；
- 后续可在 `SettingsPanel` 挂一个「开发者模式」开关（复用同一份状态）。

**为什么放前端而不是后端下发**：网格是**渲染调试信息**，不是游戏数据。
后端下发会让「正式服不渲染」变成「后端要记得不下发」，多一条可能出错的路径。
（`GraphCanvas` 因此只加一个受控的 `showGrid?: boolean`，缺省 false，保持零业务。）

### 13.2 开启时渲染什么（**这才是「方便给调整建议」的关键**）

| # | 内容 | 用途 |
| --- | --- | --- |
| 1 | **格子边框**（低透明度 token 色，1px） | 看清坐标空间 |
| 2 | **轴标**：顶部列号 `1..grid_cols`、左侧行号 `1..grid_rows` | 能直接报坐标 |
| 3 | **每个枢纽下方标注它的 `(行,列)`** | 你可以截图说「把藏书阁挪到 (8,12)」 |
| 4 | **理想环参考线**（可选）：`polarFor()` 算出的理想位画成淡色小圈 | 一眼看出哪个节点被 `sep` 推偏了 |

第 4 条把 §2.4 的「**落点最大偏移 ≤ 2 格**」这条自检**变成肉眼可见的** ——
不用跑脚本，看哪个节点的实际位置离淡色小圈最远就知道了。

**mock 已经实现了 1~3**：`tmp/map-canvas-n21.html` 顶部有个「开发者模式」复选框，
勾上就能看到网格 + 轴标 + 每个枢纽的坐标。第 4 条在正式实现时再加。

### 13.3 边界

- `showGrid` 只影响渲染，**绝不影响**落格结果、命中判定、连线派生；
- 正式构建里这段代码仍然打包（体积可忽略），但**默认分支恒为 false**；
- 单测覆盖：`?mapGrid=1` / `?mapGrid=0` / 无参数 + `DEV=true` / 无参数 + `DEV=false` / 非法值 `?mapGrid=x`（应回退到构建模式）。
