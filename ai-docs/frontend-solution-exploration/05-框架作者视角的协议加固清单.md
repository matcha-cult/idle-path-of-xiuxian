# 05 · 框架作者视角：协议加固清单（自研无社区背景下的高杠杆改造）

> 背景校正：**ionet-ts 是作者本人基于 ionet 设计思想的 TypeScript 重写，已开源但无社区热度。**
> 这改变了 04 号文档里 Q1~Q8 的性质——它们不是"求外部后端团队拍板"，而是**作者可直接排期的框架改造项**。
> 本文按优先级列出加固清单，每条给出：源码证据 → 对前端的影响 → 最小改法 → 前端随之获得的简化。

## 1. P0 · 阻塞真实实时玩法 / 或存在静默缺陷

### P0-1 响应回显 `cmd/subCmd` 与 `requestId`（请求关联能力）

**证据**
- `packages/external-server/src/websocket/ws-server.ts:138-161`：`handleMessage` 只从请求取 `{cmd, subCmd, data}`，响应仅 `createResponseMessage(result)`。
- `packages/core-framework/src/core/bar-skeleton.ts`：`execute()` 返回 `{data}` 或 `{errorCode, errorMessage}`，不含路由信息。
- 全仓 `requestId|reqId|msgId` **零命中** —— 关联能力在协议层根本不存在。

**对前端的影响**：无法并发请求（响应无任何可配对字段），只能串行队列（02 §3.2 策略 A）；面板并行加载、慢 Action 不阻塞后续请求等能力全部不可得。

**最小改法（纯增量，向后兼容）**

```ts
// ws-server.ts handleMessage 内
const req = this.codec.decode(message) as RequestMessage;
const result = await this.skeleton.execute({ cmd: req.cmd, subCmd: req.subCmd, data: req.data });
const response = {
  ...createResponseMessage(result),
  cmd: req.cmd,            // 回显
  subCmd: req.subCmd,      // 回显
  requestId: req.headers?.requestId ?? req.traceId,  // 关联
};
ws.send(this.codec.encode(response));
```

**前端收益**：`correlation: 'serial' → 'reqId'` 一行切换；响应路由可直接按 `(cmd, subCmd)` 校验（顺带防串包）。

---

### P0-2 `headers/traceId` 透传到 `FlowContext`

**证据**：协议模型里**已经有**这两个字段——`protocol/message.ts:3-9`（`RequestMessage.headers/traceId`）、`flow-context.ts:6-11`（`Request {headers?}`）；但 `ws-server.handleMessage` 把它们裁掉了，`BarSkeleton.execute` 的入参签名也只有三个字段。**模型有、路断**。

**最小改法**：`BarSkeleton.execute()` 入参加两个可选字段；`ws-server` 原样传 `headers/traceId`（`ctx.setRequest(request)` 本就接收整个对象，改动极小）。

**前端收益**：requestId、鉴权票据、语言/时区、灰度标签、全链路 traceId 都有了合法通道。

---

### P0-3 响应 / 推送的判别字段（消除一类静默 bug）

**证据**：响应信封固定为 `{data, errorCode, errorMessage}`；而推送由调用方自由构造（`ws-server.ts:177-184` `broadcast(message)` 对传入对象**原样 encode**）。

**风险**：前端串行队列收到一帧时，**无法确定性判断这是"我请求的响应"还是"服务端主动推送"**。当前只能靠"响应不带 cmd/subCmd"这一**事实约定**来区分——这是能用的，但脆弱：一旦 P0-1 给响应加上 cmd/subCmd，这个唯一的判别依据就消失了。**P0-1 与 P0-3 必须一起做。**

**最小改法**：信封增加 `kind: 'response' | 'push'`（或 `push: true`），由框架统一构造两类帧。

**前端收益**：判别从"事实约定"升级为"协议保证"，串行队列与推送可安全共存。

---

### P0-4 连接 → userId → 定向推送的链路断链（**已确认是实现缺陷，且 README 已承诺该能力**）

**证据**
- `ws-server.ts:15-19`：`ClientConnection.userId?` 被声明；
- `ws-server.ts:186-195`：`sendTo(userId, message)` **读取** `connection.userId` 做匹配；
- **全仓 grep 无任何赋值点**：`session-inout.ts:21` 与 `flow-context.ts:51` 只写 `session.userId`，**从不触碰 WS 连接对象**；
- 但 `packages/external-server/README.md` 明确写道：`ws.sendTo(100n, {...})` 且注释"**需先绑定 userId**" → 文档承诺，实现未兑现。

**结论**：`sendTo()` **永远返回 false**，服务端定向推送完全不可用。而定向推送是放置/MMO 类游戏的核心（离线结算、私人通知、异步事件）。

**最小改法**：`handleConnection` 时把连接注册进 `ConnectionRegistry`；`SessionInOut`（或 `bindingUserId` 的传输层回调）在 userId 首次绑定时更新注册表；`sendTo` 与 `broadcastToUser` 共用同一注册表。

**为何定级 P0**：这不是"能力缺失"，而是"**文档承诺了但静默失效**"——最容易在生产上踩雷的一类缺陷。现有 `websocket-server.test.ts` 覆盖了 start/valid/invalid/broadcast/clientCount/attach/选项校验，**唯独没有 `sendTo` 的测试**，这也解释了为何一直未被发现。

---

### P0-5 Broadcaster 抽象未接线（广播子系统是孤岛）

**证据**
- `Broadcaster / MemoryBroadcaster / MemoryConnectionRegistry / createMemoryBroadcaster` 全部只存在于 `core-framework/src/broadcast/**`；
- **无任何类实现 `Connection` 接口**（grep `implements Connection` 零命中）；
- `extension-nestjs/src/**` 中 `broadcast|Broadcaster|Registry` **零命中** —— 模块 providers 里没有 Broadcaster；
- 因此 `MemoryBroadcaster` 依赖的 `ConnectionRegistry` 永远是空的，该子系统当前不可用。

**影响**：Action 侧没有"向客户端推送"的正规入口；业务只能绕道拿到 `IONET_WS_SERVER` 实例直接调 `broadcast()`——而 Action 在 NestJS 集成下**拿不到 DI**（见 P1-1），形成死结。

**最小改法**：`WebSocketExternalServer` 内维护并暴露 `ConnectionRegistry` 适配器（把 `ws` 连接包成 `Connection`），`MemoryBroadcaster` 复用同一注册表，`IonetModule` 把 `Broadcaster` 作为 provider 导出。

## 2. P1 · 工程完备性（决定"后端业务 Action 化"能否落地）

### P1-1 Action 的 DI 隔离：NestJS 下 Action 拿不到任何服务

**证据**
- `extension-nestjs/src/ionet.module.ts` 的 `IonetFeatureModule` 构造器调用 `skeleton.addAction(ActionClass)`（**不传 instance**）；
- `bar-skeleton.ts` 的 `addAction(ActionClass, instance?)` 明示："未传 instance 时直接 `new ActionClass()` 实例化（**不经过外部 DI 容器**）"；
- `core-framework/src/core/action-factory-bean.ts` 存在 `ActionFactoryBean` 扩展点——但 `grep` 显示它**只在 index.ts 里被导出，全仓无任何使用**；且 `DefaultActionFactoryBean.getBean()` 也只是 `new ActionClass()`。

**影响**：真实业务 Action 无法注入 Prisma/Redis/服务——本项目 `HealthAction` 恰好零依赖，所以这个坑尚未暴露，一旦业务 Action 化就会立刻撞墙。对照 Java 版：`extension-spring` 的全部价值就是 `ActionFactoryBeanForSpring`（4 行集成）。

**最小改法**：补一个 **`ActionFactoryBeanForNest`**（对齐 Java 的 `ActionFactoryBeanForSpring`）：`forFeature({ actions, injectFromContainer: true })` 时用 `ModuleRef.get(ActionClass, { strict: false })` 取容器实例，再 `addAction(ActionClass, instance)`。

---

### P1-2 连接级鉴权钩子缺位（Java 版 UserHook 的对等物）

**证据**：`ws-server.handleMessage` 无任何鉴权检查；`ExternalServerOptions` 只有 `port/host/codec`。任何连接都可直接调用任意 Action。

**影响**：① 安全边界——未鉴权连接直达业务 Action；② 前端鉴权形态被迫收敛为"连接后首个 Action 验票"；③ 连接身份无法在握手期建立（与 P0-4 的 userId 绑定是同一个根）。

**最小改法**：`ExternalServerOptions` 增加 `onHandshake?(info) => Promise<{ userId } | null>`（WS 从 query/header 取票，HTTP 从 `Authorization` 取票）；或 `handleMessage` 前置 `verifyRequest` 钩子。

---

### P1-3 推送信封规范化

**证据**：`broadcast/types.ts:1-6` 定义 `BroadcastMessage {type, data, timestamp, fromUserId?}`——与 `{cmd, subCmd, data}` 是**两套并列的编码体系**；`ws.broadcast()` 对传入对象原样透传。

**最小改法**：统一推送信封 `{ kind:'push', cmd?, subCmd?, type?, data, timestamp }`，由框架构造，禁止业务自造形状。

**前端收益**：推送路由从"双形态容错"（02 §3.4）简化为单一路由表。

---

### P1-4 codegen 与线协议对齐

**证据**：`typescript-generator.ts` 生成的 Response 接口包含 `cmd/subCmd`，而线协议响应没有 → 生成物与实现相互矛盾（01 §7 已记录）。

**处置**：P0-1 落地后自动一致；若不改协议，则从生成器里删掉这两字段。另：codegen 目前只产出"常量 + 接口"，**没有可运行的客户端调用代码**（无 transport/correlation）——建议 codegen 只产出 DTO + Commands，运行时直接复用 `ionet-client`（02 §3），避免两套实现漂移。

## 3. P2 · 演进项

### P2-1 二进制编解码的跨端契约
jprotobuf 的 `[1B typeName 长度][typeName][protobuf 载荷]` 是移植版**私有**自描述格式；跨语言客户端需要"typeName 注册表 + 字段 schema（tag/type）"。建议框架导出**机器可读 schema 清单**，或改以标准 `.proto` 作为唯一真相（对"无数语言客户端"的目标更友好）。

### P2-2 HTTP fallback 提升为正式的第二传输（**现成的韧性方案**）
**事实**：`HttpExternalServer` 已提供 `POST /{prefix}/{cmd}/{subCmd}`，**与 WS 完全相同的 Action 路由与响应信封**（`http-server.ts:80-95`），请求体兼容裸 DTO 与 `{data}` 包装，HTTP 状态码按 `errorCode >= 400` 映射。

**价值**：企业代理、弱网、部分小程序环境不支持 WS 时，可**零后端改动**降级为 HTTP 调用同一 Action——对"PC + 手机浏览器"是极实用的兜底。

**注意**：HTTP 路径 `/api/{cmd}/{subCmd}` 与 NestJS REST 的 `/api` 前缀会冲突，部署时需分开前缀（如 REST 用 `/api`，ionet HTTP 用 `/ionet`）。建议把该 URL 约定写进协议规格（目前只在 README）。

## 4. 改动 → 前端架构的连锁简化

| 框架改造 | 前端 v1（当前设计） | 前端改后 | 影响面 |
|---|---|---|---|
| P0-1 reqId + cmd 回显 | 串行队列，同时刻仅 1 个未决请求 | 并发请求，面板并行加载；串行降为兜底 | SDK correlation 模块一行配置 |
| P0-3 `kind` 判别 | 靠"响应无 cmd"事实约定区分推送 | 协议保证判别 | 分发逻辑简化，消除一类静默 bug |
| P0-2 headers 透传 | 无 | traceId / 灰度 / 语言走 headers | API 层可选增强 |
| P0-4 / P0-5 推送链路 | 服务端无法主动推 | 实时玩法成立（离线结算、私人通知） | 业务层新增订阅与 store action |
| P1-2 握手鉴权 | 首 Action 验票 | 连接即鉴权、握手期绑定身份 | SDK `authHandler` 形态确定 |
| P1-1 Action DI | Action 无法访问服务 | Action 可注入 Prisma/Redis | 后端业务 Action 化的前置条件 |
| P2-2 HTTP fallback | 无 | WS 不通自动降级 | 新增一个 Transport 适配器 |

## 5. 建议排期与工作量

**顺序**（相对"先做完前端再回头改协议"的风险）：

1. **P0-4 / P0-5**（推送链路断链 + Broadcaster 接线）——先修"文档承诺却静默失效"的确定性缺陷；
2. **P0-1 / P0-2**（关联 + headers 透传）——前端并发与可追踪性的地基；
3. **P0-3**（判别字段）——与 P0-1 同批，否则唯一判别依据会消失；
4. **P1-2**（握手鉴权）→ **P1-1**（Action DI）→ P1-3/P1-4 → P2。

**工作量粗估**
- P0-1~P0-3：集中在 `ws-server.ts` / `bar-skeleton.ts` / `protocol/message.ts` 三处，**小改动**；
- P0-4/P0-5：需引入"连接↔userId 注册表"并接线 NestJS，**中等改动**；
- P1-1：新增 `ActionFactoryBeanForNest` + `forFeature` 选项，**中等改动**；
- 每条都应补 WS 集成测试（现有 `websocket-server.test.ts` 未覆盖 `sendTo`，正好补上）。

**若暂不改协议**：前端 v1 的兼容策略已在 02 落地（串行队列 + 双形态推送路由 + "无 cmd 即响应"事实判别），可以先跑通；但必须在 SDK 源码里把这些"事实约定"写成显眼注释，防止后人误用。
