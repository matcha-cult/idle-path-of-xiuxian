## 0. 一句话结论

**秘境不再是地图上的节点，而是「靠在第八峰·后山的一块石台上、用在线战斗打出来」的独立副本。**
每个秘境 **3 层**；**打通 3 层 = 突破成功 = 该秘境被解锁**，随之出现在**秘境页面**；
未突破的秘境**在秘境页面完全不出现**。1~5 境免费，6~13 境需道具（后期实装）。
已解锁的秘境可反复挑战；**能挂机的只有可反复挑战的那一类**；**在线战斗期间离线挂机强制关闭**。

## 2. 术语与三态状态机

### 2.1 三个词，三个不同东西（**此前一直混用，这是本轮的主要混乱源**）

| 词 | 含义 | 落在哪 |
| --- | --- | --- |
| **突破（breakthrough）** | **动作**：与石台对象交互 → 选一个秘境 → 进入在线战斗，目标打满 3 层 | `zone.breakthrough` |
| **解锁（unlock）** | **结果**：该秘境通关 3 层 → `cleared` → 出现在秘境页面 | `game_zone_progress.cleared` |
| **挂机（idle）** | **另一条线**：离线时间兑换产出，目标是一个**已解锁且允许挂机**的秘境 | `game_idle_state` |

> **「突破」不是「解锁」的同义词**：可以突破失败（进去送人头），那就不解锁。
> 用户原话「突破后的秘境在秘境页面直接可见」= **突破成功**之后。

### 2.2 状态机

```
        ┌──────────────── 地图（idle） ────────────────┐
        │  game_zone_state 无行 ⇒ 离线挂机可用           │
        └───────┬───────────────────────────▲───────────┘
                │ 对象交互「突破」            │ 打满3层自动退出 / 手动退出
                ▼                            │
        ┌──────────────── 在线战斗（online） ──────────┐
        │  game_zone_state 有行 ⇒ **离线挂机强制关闭**  │
        │  P3.0 在线 tick 推进层数（1→2→3）             │
        └───────┬──────────────────────────────────────┘
                │ 第 3 层打完
                ▼
        cleared = TRUE  ⇒  秘境页面出现该秘境
                │
                ├── 「重复挑战」→ 回到在线战斗（层数循环 1→2→3）
                └── 「设为挂机点」→ 回到地图，离线挂机指向它
```

**互斥的**唯一判据**（一行，可测）：`game_zone_state` 有该角色一行 ⇒ 离线挂机暂停。**

> ⚠️ **现在没有「离开秘境」这条路**。`zone.enter` 之后 `game_zone_state` 永久有行，
> 于是「在线战斗时关闭离线挂机」会**一旦触发就永远关着**。**必须新增 `zone.leave`**（§6.3）。

## 4. 数值：不是推翻，而是找到了 `zone_houshan` 背后的公式

### 4.1 关键发现

P3.0 刚调好的 `zone_houshan`（4 境 / 3 层 / **75·87·99** / 层灵韵 **8**）
**正好是下面这条公式在 N=4 的取值**：

```
base_power(N)            = 20 × N − 5        →  N=4 ⇒ 75     ✅
power_step               = 12                →  75, 87, 99   ✅
lingyun_bonus_per_floor  = 2 × N             →  N=4 ⇒ 8      ✅
max_floor                = 3                 →  3            ✅
boss_every_floors        = 3                 → 第 3 层是 Boss ✅
tier_bonus_every_floors  = 0                 →  0            ✅
drop_bonus_every_floors  = 1                 →  1            ✅
```

**七个数一个不差。** 所以「全删重做」删掉的只是那 6 行脏数据，
**用户刚调好的手感被完整保留并推广到了 1~13 境** —— 这是本轮设计最省事的一点。

### 4.2 为什么 `20N` 是对的

战力公式（`app.config.json` → `zonePower`）：

```
playerPower = realm × 20  +  已装备件数 × 5  +  floor(功法等级和 / 2)
              └─白板─┘      └──装备──┘         └────功法────┘
```

- **`20N−5` = 该境界白板战力 × 0.95** → 白板刚好能过第 1 层（差 5 点，随手一件装备就补上）；
- **第 3 层 `20N+19` = 白板 + 19** → 约需 4 件装备 / 若干功法等级才够，**"送人头"与"能通关"有清晰分界**；
- 每层 +12 ≈ 半个装备位，3 层跨度小而可感。

> 这套数值下，`zone_r4` 的 3 层就是用户已经实测过手感的 75·87·99，
> 而 P3.0 实测「约 1 分钟打通 3 层」。**其余 12 个秘境的手感预期与之一致。**

### 4.3 待调的旋钮（🟡 不阻塞）

| 旋钮 | 现值 | 说明 |
| --- | --- | --- |
| `powerStep` | 12（固定） | 若高境界想要更陡，可改 `6 + N`（13 境 ⇒ 19/层）；**但现在固定 12 是唯一被实测过的** |
| `killsPerFloor`（P3.0） | 30 | 决定"打满 3 层"多久。P3.0 实测约 1 分钟，用户当时**没有反对** |
| 层灵韵 `2N` | 2…26 | 旧库是 2/5/10/18/30（更陡）。**改用线性 `2N` 是按 3 层秘境重推的** |

## 5. 数据模型改动

### 5.1 `game_zones`（重灌，字段级改动）

**删列**

| 列 | 理由 |
| --- | --- |
| `require_prev_best_floor` | 链式解锁**作废**（用户 Q2：解锁条件 = 通关 3 层，与前置秘境无关） |
| `min_realm` | **语义作废**：境界不再是闸门。改名为 `realm` 表示"这是第几境的秘境" |
| `chapter` | 秘境不再属于章节（章节的 `zone_code` 连坐见 §9.1） |

**加列**

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `realm` | `INTEGER NOT NULL` | 该秘境对应的境界 1~13（**展示 + 数值档位**，不是闸门） |
| `tier_kind` | `VARCHAR(16) NOT NULL` | `'training'` 历练 / `'special'` 特殊 |
| `unlock_item_code` | `VARCHAR(64) NULL` | 突破所需道具（`tier_kind='special'` 时非空；**本轮只留字段 + 展示，不消耗**） |
| `idle_allowed` | `BOOLEAN NOT NULL` | 能否挂机（`training`=true / `special`=false） |

**保留列**：`code / name / order_index / unit_code / boss_code / base_power / power_step /
max_floor / lingyun_bonus_per_floor / boss_every_floors / tier_bonus_every_floors / drop_bonus_every_floors`

**删除的 6 行**：`zone_qingyun / zone_miwu / zone_guhai / zone_dajie / zone_hundun / zone_houshan`。

### 5.2 `game_zone_progress`（**玩家数据**，语义扩展）

保留 `floor / best_floor / cleared`，新增：

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `clears` | `INTEGER NOT NULL DEFAULT 0` | 通关次数（重复挑战每打满一轮 +1）——**这是"已解锁"的证据，也是重复挑战的计数** |

> `cleared` 与 `clears` 的关系：`clears ≥ 1` ⇒ `cleared = TRUE`。两者同时维护是为了
> 让 `cleared` 继续兼容既有 SQL（`advanceFloor` / `challenge`），`clears` 单独给"周目数"用。
> **⚠️ 玩家数据不 DELETE**（§9.2 有迁移脚本）。

### 5.3 `game_idle_state`（**新表**）—— 挂机点

```sql
CREATE TABLE IF NOT EXISTS game_idle_state (
  id           SERIAL PRIMARY KEY,
  character_id INTEGER NOT NULL UNIQUE,
  zone_id      INTEGER NOT NULL,          -- 挂机目标秘境
  updated_at   TIMESTAMP(6) NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

**为什么要新表而不是复用 `game_zone_state`**：

| 表 | 语义 |
| --- | --- |
| `game_zone_state.current_zone_id` | **在线战斗所在**（有行 = 在线 ⇒ 挂机暂停） |
| `game_idle_state.zone_id` | **离线挂机目标**（离线时用） |

两件事本来就可以同时存在（打 A 挂 B），塞一张表会让"互斥"这条规则无法表达。

### 6.2 `unlockInfo` / `unlockInfo` 的链式逻辑 **整体删除**

`zone.service.ts` 里的 `UnlockInfo`、`unlockInfo()`、`realmTooLow()`、`zoneLocked()`、
`require_prev_best_floor` 相关分支 **全部删除**。新的准入判定只有两句：

```
可突破 ⇔ (tier_kind='training') ∨ (tier_kind='special' ∧ 持有 unlock_item_code)
已解锁 ⇔ game_zone_progress.cleared = TRUE
可挂机 ⇔ 已解锁 ∧ idle_allowed
```

### 6.3 ⚠️ P3.0 在线 tick 的**硬依赖**必须拆掉（本设计最重要的一处手术）

现状（`online-explore.service.ts`）：

```ts
const node = await this.mapLogic.secretRealmNodeView(characterId, context.zoneCode);
if (!node) return null;          // ← 没有 secret_realm 地图节点 ⇒ 在线 tick 直接不跑
```

**一旦第八峰不再是 `secret_realm` 节点，整个在线打怪当场失效。** 必须改成：

```ts
// 在线判据改为「有在线战斗会话」，与地图节点彻底解耦
const state = await this.zoneService.onlineBattleState(characterId);   // game_zone_state
if (!state) return null;
```

**连带退场**（这三处都是 20 §3.5 里点名的过渡债，现在正好到期）：

| 位置 | 处置 |
| --- | --- |
| `map.service.secretRealmNodeView()` | **删除**（唯一用途就是在线上闸门） |
| `map.service.zoneIdleGate()` 的 `enforced` 过渡分支 | **删除**（代码注释里的退场条件——"5 个遗留秘境被重新归属"——**本轮达成**） |
| `map.service.onZoneFloorPassed()` | **删除**，连带 `game_node_progress.idle_unlocked` 不再被写（挂机闸门改由 `zone.idle_allowed + cleared` 承担） |

> `game_node_progress.idle_unlocked` 列**保留**（玩家数据），只是不再有新写入；
> 是否物理删列见 §10 🟡Q6。

### 6.4 `idle` 域

```ts
// idle.service.settle() 前置：在线战斗期间强制关闭离线挂机（用户 Q6）
if (await this.zoneLogic.inOnlineBattle(character.id)) {
  return fail('ONLINE_BATTLE_ACTIVE', '在线战斗中，离线挂机已暂停');
}
```

结算目标改为：`game_idle_state.zone_id`（**不再用 `currentZoneId` 的"最低 order 兜底"**）。
若没设过挂机点 → `fail('IDLE_TARGET_NOT_SET', '尚未设置挂机点')`。

**挂机打哪一层**：建议**该秘境第 3 层**（`max_floor`，产出最高），
`lingyunBonus = max_floor × lingyun_bonus_per_floor`。见 §10 🟡Q5。

**Q2 · 「1~5 境秘境免费」怎么读？**
我的读法：**"1~5 境的秘境不要道具，任何境界的角色都能突破它们"**（免费是给秘境的，不是给角色的）。
另一种读法：**"1~5 境的角色突破免费，6 境以上角色要道具"**。
**这两个读法会导出完全不同的闸门代码**，请指认。

**Q3 · 打满 3 层之后，角色是"自动退出秘境"还是"留在里面继续刷"？**
我倾向**自动退出**（回地图，挂机恢复），因为用户 Q6 要求"在线战斗时关闭离线挂机"——
如果打满还留在里面，挂机就永远关着。**但这也意味着"在线重复挑战"要再点一次。**
（若选"留在里面"，就必须给一个明确的「离开秘境」按钮，且挂机在离开前一直关着。）

**Q4 · `game_zones` 的 6 行是 `DELETE` 还是保留成"废弃数据"？**
用户说"全删"。我按 **DELETE** 设计（连带 §9.2 的孤儿清理）。
