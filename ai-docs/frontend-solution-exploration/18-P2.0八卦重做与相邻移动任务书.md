## 3. ⚠️ 一院多职能 ⇒ 必须引入**对象层**（本轮做「显示 + 入口」，交互留 P2.1）

现在 `game_map_nodes.feature_key` 是**单值**，一个院挂 2 个职能表达不了。
本仓 `schema.prisma` **没有任何 `Json` 列**（已查），所以不用 JSONB 凑，
直接建正经的对象表 —— 这也是 P2.1（NPC/传送点/秘境入口对象化）的基础：

```prisma
model game_map_objects {
  id          Int      @id @default(autoincrement())
  code        String   @unique @db.VarChar(50)
  map_id      Int
  node_code   String   @db.VarChar(50)   // 宿主枢纽（四院或主峰）
  kind        String   @db.VarChar(20)   // office = 职能入口（本轮唯一类型）
  name        String   @db.VarChar(50)   // 如「藏经阁」
  feature_key String?  @db.VarChar(20)   // 要打开的系统
  description String?  @db.Text
  order_index Int
  created_at  DateTime @default(now()) @db.Timestamp(6)
  updated_at  DateTime @updatedAt @db.Timestamp(6)

  @@index([map_id, node_code, order_index])
}
```

**本轮范围**：11 个对象（4 院 ×2 + 主峰 ×3），`map.list` 全量下发，右栏按宿主枢纽列出。
**不做** `map.interact`、不做对象进度表 —— 点击对象仍走 **P1 已有的 `FeatureGate`**
（系统未实现 → 「未开放」；已实现 → 跳既有面板）。`kind` 只出现 `office` 一种。

> 节点上的 `feature_key` **保留**（作为该院的「主职能」，用于图例与 Tooltip），
> 与对象表**不冲突**：对象表是明细，节点列是摘要。

## 4. 邻接表：**由落格算法派生**（不再手写）

> **用户指出的问题（2026-09-14）**：
> 「比如西门相邻是第二、第三峰，同时他们是执法院的相邻点，
> 但是按目前来看，**这个相邻很容易出现数据定义错位**。」
>
> **这个担心成立**：手写边表会和画布漂移 —— 人在种子 JSON 里挪一个坐标，边表不会跟着动，
> 于是「画出来的线」和「实际能走的路」对不上。
> **解法：边不是独立数据，而是几何的函数。**

### 4.1 派生规则（确定性，**零手写**）

落格完成后，按**极坐标结构**派生全部边：

| 规则 | 说明 |
| --- | --- |
| **同环相邻** | 同一环（八峰环 / 四院环）上**角度相邻**的两点连边（环是闭合的） |
| **门 → 峰** | 每座山门连**角度最近的 2 座峰**（左右各一） |
| **峰 → 院** | 每座峰连**角度最近的 1 座院** |
| **院 → 主峰** | 四院各自连青云主峰 |

**用用户的例子验证（已实测，逐条吻合）**：
西门在 `180°`；八峰在 `247.5/202.5/157.5/112.5/67.5/22.5/337.5/292.5°`。

```
角度上离西门最近的 2 座峰 → 第三峰(157.5°，差 22.5°)、第二峰(202.5°，差 22.5°)   ✓
第三峰 角度最近的院 → 执法院(180°，差 22.5°)                                      ✓
第二峰 角度最近的院 → 执法院(180°，差 22.5°)                                      ✓
```

派生结果 **32 条**（八峰环 8 + 门→峰 8 + 峰→院 8 + 院环 4 + 院→主峰 4）。
**实现要求**：`gen-map-seed.mjs` 里写一个**纯函数 `deriveEdges(cell, nodes)`**，
边表由它产出；**种子 JSON 里存的是它的输出**（保持运行时架构不变，仍读 `game_map_edges`）。

### 4.2 新增**结构性自检**（防「数据定义错位」的关键）

对每一条边**硬性断言**两端满足下面**之一**，否则**硬失败**：

1. **同环且角度相邻**（角度差 = 该环步长，八峰 45° / 四院 90°）；
2. **相邻环且角度最近**（一端的角度，落在另一端所在环上最近的那个）。

> 作用：**任何手改种子把边改歪，种子生成阶段就炸**，而不是上线后让玩家发现
> 「这条线连着两个挨不着的点」。它保证 **画出来的线 ≡ 可走的路 ≡ 边表**
> —— 三者同一份数据，结构上不可能错位。

另外保留 P1 已有的**软提示**（不失败、只打印）：边跨度直方图、**连线交叉数**、不相邻最小间距。
去掉外门接引区后交叉数应显著下降，**把实测值写进报告**。

## 7. 测试要求

**服务端**：
- 新角色 `map.list` 返回 **17 个节点**，`adjacent === true` 的恰好 **4** 个（四门）；
- 返回 **11 个对象**，每个的 `nodeCode` 都是四院或主峰之一；`featureKey` 非空；
- `map.enter` 到**相邻**节点 → 成功且 `current_node_id` 更新；
- `map.enter` 到**不相邻**且非山门 → **`NODE_NOT_ADJACENT`**（防回归核心）；
- **`map.enter` 到相邻但战力远低于门槛的节点 → 仍然成功**（战力限制已删除，防回归）；

  改成「同环但不相邻」→ 也必须失败（这是防「数据定义错位」的关键用例）；

  `objects = []`、节点的对象宿主不存在。
