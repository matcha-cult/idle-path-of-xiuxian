## 1. 挂机后端现状（**已实现、已实测，改前端不会碰它**）

### 1.1 协议面

| 动作 | 说明 |
| --- | --- |
| `zone.idleTarget` **(100,9)** | `{ zoneCode }` → 设挂机点。**准入：已突破（`clears ≥ 1`）∧ `idle_allowed`**；否则 `ZONE_NOT_IDLE_ELIGIBLE` |
| `zone.zones` **(100,1)** | `data.idleTarget` = 当前挂机点 code（null = 未设置）；`data.zones` = 已突破秘境；`data.breakthrough` = 全 13 境 |
| `idle.status` **(130,1)** | 离线时长 / 预计击杀 / 预计灵韵 / 今日物品上限 / 配置（60 轮·时、60%、12h 上限） |
| `idle.settle` **(130,2)** | 结算离线收益。**闸门顺序（真后端 e2e 抓出并修正）**：① 参数校验 → ② `ONLINE_BATTLE_ACTIVE` → ③「暂无可结算收益」早退 → ④ `IDLE_TARGET_NOT_SET` → ⑤ 结算 |

### 1.2 数据

```sql
game_idle_state(id, character_id UNIQUE, zone_id, updated_at)   -- 一人一个挂机点
game_idle_counters(character_id, day, items_produced)           -- 每日物品上限 200
characters.last_settle_at                                        -- 计时锚点
```

### 1.3 结算口径（`idle.service.ts`）

```
有效小时 = min(离线小时, 12) × 60%
击杀数   = floor(离线小时 × 60 轮/时 × 60%)
单位     = idleEncounter(characterId) → 挂机点秘境，floor = min(progress.floor, maxFloor)
           ⚠️ 已突破秘境的 progress.floor = maxFloor = 第 3 层 = **Boss 层** ⇒ 挂机**打在 Boss 上**
产出     = combatLogic.settleKills(kills, { itemBudget: 200 - 今日已产 })  -- 既有辨宝法阵
```

### 1.4 硬不变式（**绝不能破坏**）

1. **离线时间只能兑换产出，不能兑换进度**：挂机**不涨层、不给 `clears`、不写 `game_zone_progress`**（现实现已如此）；
2. 客户端**不本地算产出**（R2 §4.2）；
3. 在线战斗期间（`game_zone_state` 有行）挂机**被拒**（`ONLINE_BATTLE_ACTIVE`）；
4. 特殊秘境（6~13 境）**不可挂机**（`idle_allowed = false`）；
5. 未突破的秘境**不可设为挂机点**。

## 3. ⚠️ 动手前必须拍板的设计问题（**这是本轮真正需要用户输入的部分**）

> 下面每条都会改变实现与数值，不是"随手选"。已给出我的倾向与理由，用户可直接指认。

### 🔴 A. 挂机产出打哪一层？（影响掉落表与数值，必须先定）

现状：`floor = min(progress.floor, maxFloor)`，而已突破秘境 `floor = 3 = maxFloor = Boss 层`
⇒ **挂机一直在打 Boss**（`unit_code = boss_code`，并吃 `zoneBossExtraDraws` 额外掉落判定）。

| 选项 | 说明 | 我的倾向 |
| --- | --- | --- |
| **A1** 保持打最深层（= Boss 层） | 产出最高；但等于「无限刷 Boss」，Boss 掉落不再稀缺 | ✗ |
| **A2** 只打**普通层**（第 1 层） | 与 D3「挂机点 = 保底」一致；Boss 掉落只属于在线打出来的成绩 | ✅ **推荐** |
| **A3** 循环整轮（1→2→3 平均） | 折中，也能吃到一点 Boss 产出 | 可接受 |

### 🔴 B. 挂机是「手动结算」还是「自动结算」？

现状：**手动** —— 挂机面板上点「结算离线收益」才 roll（`idle.settle`）。

| 选项 | 说明 |
| --- | --- |
| **B1** 保持手动 | 改动最小；但玩家不点就没有收益，容易以为坏了 |
| **B2** 上线/进挂机面板时自动结算一次 | 常见放置游戏做法；需要前端在适当时机调一次 `idle.settle`（并弹结算） |
| **B3** 在线期间定时自动结算 | 需要后端加节拍（与在线 tick 同类受管定时器） |

> 我倾向 **B2**（进入游戏/打开挂机面板时自动结算并展示明细），保留手动「再结算」为刷新。

### 🔴 C. 「挂机」到底指哪种语义？（**最容易被误解的一条**）

本作现状是**离线收益**：按 `characters.last_settle_at` 到现在的**真实时间差**兑换产出，
**不要求玩家在线**（R2 §4.2 明令不做离线补算的是"在线 tick"，而离线收益本来就是按时间差算的）。

而"挂机"在中文里也常被理解为「**在线**自动打怪」。请确认：

- **C1** = 离线收益（现状）：关掉游戏也在攒，回来一键收。（推荐，与 P4.2 / R2 一致）
- **C2** = 在线自动战斗：需要一套新的"在线挂机"循环（与现有在线 tick 的秘境战斗区分开）。
- **C3** = 两者都要（离线攒 + 在线自动打），需要明确两者互斥与叠加规则。

### 🟡 D. 挂机与在线战斗的**每日物品上限**是否统一？

现状：挂机物品有**每日 200 上限**（`game_idle_counters`）；在线战斗 `settleKills` **不受该上限约束**。
统一会改变在线收益，需谨慎 —— 建议**本轮不动**（只记录）。

### 🟡 E. 数值是否重标定？

现状：`60 轮/时 × 60% × 12h = 432 击杀/次`，而在线涨一层需 `killsPerFloor = 30`
⇒ 挂机 1 小时 ≈ 1.2 层的击杀量。是否按"挂机满 12 小时 ≈ 通关 N 轮"重新标定？
（注意：挂机**不给进度**，所以这只是产出量级问题。）

### 🟡 F. 挂机点数量

现状 `UNIQUE(character_id)` = **一人一个**。是否要多挂机点？（建议保持 1 个，改动最小）

### 🟡 G. 玩家在秘境里切后台时，挂机算不算在攒？

现状：在线 tick 在 `hidden`/`no_session` 时暂停，但**挂机结算仍会因 `game_zone_state` 有行被拒** ——
即"人在秘境里（哪怕切后台）就不能收挂机收益，必须离开秘境"。
这条**符合 A/B 之外的直觉吗**？若不符合，需要放宽 `ONLINE_BATTLE_ACTIVE` 的判据（例如只拦"页面可见"）。
