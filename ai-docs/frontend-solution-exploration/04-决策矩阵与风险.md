## 1. 决策矩阵（已定结论）

| # | 决策点 | 结论 | 依据 |
|---|---|---|---|
| D1 | 前端与后端耦合关系 | **零耦合**：前端只认线协议（`{cmd,subCmd,data}` 文本帧）；严禁 import `@nbb-ionet/*` | 01 §9：core-framework 依赖 node:async_hooks，浏览器不可用；01 §3：协议是唯一契约 |

| D3 | SDK 形态 | 自建 `packages/ionet-client`，零运行时依赖、环境无关、可独立发布 | 02 §3：适配器 + codec + 关联策略三接口 |
| D4 | 请求关联 | **v1 用串行队列**，SDK 保留 `reqId` 升级位 | 01 §3.2：响应无 cmd 回显/无 reqId；02 §3.2 对比表 |
| D5 | 心跳 | 应用层 `system.ping` 心跳（15s/10s）+ 平台生命周期感知 | 01 §4：WS ping/pong 对 JS 不可见 |
| D6 | 技术栈 | React + Vite + MobX 6（legacy 装饰器）+ TS 5.x + pnpm + vitest | 03 全文 |

| D8 | 类型同步 | `shared-types` 包手工镜像 + codegen 产物脚本化同步（以线协议为准） | 01 §7：codegen 响应接口与线协议不一致 |
| D9 | 多端 | 浏览器先落地；小程序只加 `SocketAdapter` + 平台工具，业务零改动 | 02 §5 差异表 |
| D10 | 工程位置 | 本仓库 `packages/web` + `packages/ionet-client` + `packages/shared-types` | 02 §4.3 |

## 2. 风险清单与缓解

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | **后端生产形态未定**：`extension-nestjs` 在 `NODE_ENV=production` 拒绝启动，注释指向"生产用 Java External Server" | 高 | 前端契约以「JSON 信封 + 文本帧」为准，Codec 可插拔，未来 Java/TS 服务端切换只换 URL 与 codec；与后端约定「协议契约文档」（本 01 号文档）为唯一事实源 |
| R2 | 响应无关联字段，并发请求无法配对 | 高 | 串行队列 v1（放置游戏请求率低，够用）；reqId 升级位已设计 |
| R3 | codegen 产物与线协议不一致（Response 接口含 cmd/subCmd） | 中 | 不信任生成接口；`shared-types` 以 01 §3 契约为准独立维护 |
| R4 | jprotobuf 二进制格式为移植版私有设计（类型前缀自描述），跨端实现有对齐成本 | 中 | v1 只用 JSON；若启用二进制，双方按「typeName 注册表 + 字段 schema」对齐；SDK 的 EnvelopeCodec 接口已预留 |
| R5 | 浏览器 WS 不支持自定义 header → 鉴权形态受限（query/ticket/首 Action） | 中 | SDK 三形态钩子（02 §3.5）；最终形态待后端拍板 |
| R6 | 移动浏览器后台冻结/掐断 WS | 中 | visibilitychange/onLine 主动断开 + 前台退避重连 + 断线 UI（02 §3.3） |
| R7 | 服务器静默期与"心跳超时判死"的边界 | 低 | 用 ping Action 的响应做唯一可预期信号，与业务静默解耦（02 §3.3） |
| R8 | 装饰器配置漂移（工具链升级踩坑） | 低 | 基座 tsconfig + 三连闸 CI + 装饰器冒烟用例（03 §5） |

## 3. 待后端确认的开放问题（前端已留缝，等待拍板）

> 这些问题**不阻塞**前端开工（v1 均按"最保守事实"实现），但拍板后前端只需局部调整。

| # | 问题 | 前端现状 | 拍板后的动作 |
|---|---|---|---|
| Q1 | WS 鉴权形态：`?token=` / header（仅小程序） / 连接后首个 Action 验票 / Java 版 UserHook 风格 | 三形态钩子预留（02 §3.5） | 确定一种，`IonetClientOptions` 指定 |
| Q2 | 是否会回显 `reqId`（走 headers 透传） | 默认串行队列；`correlation: 'reqId'` 一行切换（02 §3.2） | 支持 → 前端开启并发 |
| Q3 | 广播/推送信封统一规范（`{cmd,subCmd,data}` 还是 `{type,data}` 还是两者） | 双形态容错路由（02 §3.4） | 确定后收敛为单一路由优先序 |
| Q4 | 应用层心跳 Action 归属（是否用 `SYSTEM_CMD.ping` cmd=1/subCmd=1） | 默认复用 system.ping（01 §3 已有该 Action） | 确认 cmd/subCmd 编号 |
| Q5 | 业务错误码表（0=成功以外的分布） | 统一归一化错误 + 文案映射（02 §4.1 ToastStore） | 后端给出码表 → 前端建映射表 |
| Q6 | 响应是否携带 `serverTime`（时间同步用） | SDK 时钟偏差估算已实现（02 §3.6） | 响应带字段 → 前端直接消费 |
| Q7 | 生产是否启用 ionet-ts WS（含 attach 单端口 / 独立端口 / Java External） | URL 与 codec 配置化 | 确定部署形态 → 前端环境配置 |
| Q8 | HTTP API 与 WS 的会话票据是否同源（JWT 共用？） | 假设共用 JWT + 可刷新（02 §3.5） | 确认 → 调整 SessionStore |

## 4. 里程碑建议

| 里程碑 | 内容 | 验收标准 |
|---|---|---|
| **M0 · 协议桩**（0.5~1 周） | `shared-types` + 迷你 WS mock server（复刻 01 §3 行为） | 协议快照测试通过；mock server 可被任意语言客户端连接 |
| **M1 · SDK**（1~2 周） | `ionet-client`：JSON codec、BrowserSocketAdapter、串行关联、心跳、退避重连、双形态推送路由、假适配器测试 | 跑通"连上 mock → 心跳 → 请求/响应 → 推送订阅" |
| **M2 · 应用骨架**（1~2 周） | Vite + React + MobX 骨架、RootStore、ConnectionStore/SessionStore/ToastStore、登录页、连接状态条、装饰器冒烟用例进 CI | PC + 移动浏览器登录 + ping 全链路可达；三连闸绿 |
| **M3 · 业务接入**（2~4 周） | 角色/物品/境界/放置 store 与 gameApi 对接（REST + WS 双通道） | 核心玩法在浏览器可玩；错误码文案全覆盖 |
| **M4 · 多端验证**（后续） | 微信/QQ SocketAdapter + 平台工具模块（02 §5） | 小程序环境跑通 02 §5 差异表全部行 |
