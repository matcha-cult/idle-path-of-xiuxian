## 1. 选了哪条路线 + 为什么

用户 2026-09-15 拍板：**「前端我倾向于是使用canvas画布进行绘制」** + 选项「直接上 ② 混合 canvas」。

### 选定：② 混合 canvas

| 层 | 用什么 | 为什么 |
| --- | --- | --- |
| 点阵 / 开发者网格 / 连线 | **canvas 2D** | 屏幕空间矢量重绘 → 放大**天然锐利**（旧版是把 SVG 世界层 `scale()` 放大）；且 canvas 里没有文本节点，**轴标不再被浏览器选中** |
| 枢纽（图标 / 名字 / 点击热区） | **DOM**（绝对定位） | 枢纽必须能放 antd 组件与 token 主题（`19 §10` 的硬结论）；无障碍、键盘、测试都白拿 |
| 位姿（zoom/pan） | 自写状态机（`pose-store`） | 与渲染解耦，可脱离 React 单测（见 §3 的量化） |

### 被放弃 / 未选的路线（诚实记录）

| 路线 | 为什么没选 |
| --- | --- |
| **① 换成熟手势库**（`@use-gesture/react` 等） | 用户选了 ②。且**本轮不需要**：三条手势手写在一个可单测的状态机里（`pointer-machine.ts`）就够了。隔离已经做好 —— 若手感仍不够，**只需替换 `use-canvas-viewport.ts` 这一个文件**，`CanvasGraph` 的 props 与地图页面都不用动。 |
| **③ 全 canvas** | `19 §10` 列了四条硬代价（antd 塞不进 canvas、无障碍要另维护 DOM、测试要 mock canvas、token 手动喂），且 17 个枢纽离 canvas 的性能门槛差两个数量级。**本轮未做，但把其中两条代价的实际解法验证过了**：token 喂给绘制的代价被压成 `palette.ts`（58 行纯映射）；「测试要 mock canvas」被压成「给 `paint.ts` 收窄一个最小 2D 接口」，**不需要装原生 `canvas` 包**（`paint.test.ts` 用假 ctx 跑了 12 例）。 |
| **继续修 div+css 版** | 用户已判定那是技术选型问题，且明确要求「不能在存量临时方案中直接进行修改」。**旧实现一行未动**，作为对照与回退同时保留。 |
| SVG 备选 | 用户说「有靠谱的 svg 方案也可以作为备选」。**旧入口就是 SVG+div 版**，本轮把它作为现场对照保留（打开旧入口即可 A/B）。没有另写第二份 SVG 实现 —— 那会得到与旧版同构的东西，收益低。 |

## 3. ⭐ 实测数字（手感与其他可比项）

### 3.1 React 提交次数：同一次运行里的直接对比

**这是「手感」里唯一能被机器确定性量化的部分**，由 `CanvasGraph/index.test.tsx` 实测（`React.Profiler` 计提交次数；
每个 `pointermove` 单独一次 `act()` —— 浏览器里每次指针事件是独立任务，React 18 的批处理只在单个事件内生效）：

```
[手感基线] 60 帧拖动 React 提交次数：CanvasGraph=0，GraphCanvas=60
```

| 实现 | 60 帧拖动的 React 提交次数 | 每帧做了什么 |
| --- | --- | --- |
| **新 `CanvasGraph`** | **0** | 只调 `onPose` → 重绘 canvas + 写 17 个枢纽的 `transform` |
| 旧 `GraphCanvas` | **60** | 每帧 `setPan` → 每帧一次 React 渲染 + 17 个枢纽重新协调 |

> 这条不是"更好看"，而是**掉帧的直接来源**：旧实现把渲染工作绑在了 React 提交上，
> 拖动时每帧都要 diff 整棵子树；新实现把这一路径完全移出 React。

### 3.2 三条手感问题的正面修法（逐条对应旧实现的缺陷）

| # | 旧实现 | 新实现 | 可复现证据 |
| --- | --- | --- | --- |
| 1 | **只有 `Ctrl+滚轮` 缩放**（普通滚轮被放行给页面） | **画布内普通滚轮即缩放**（以光标为锚点）；`Ctrl/⌘+滚轮` 步进更细（1.04 vs 1.12） | `pointer-machine`/`viewport-math` 用例 + `index.test.tsx` 「鼠标滚轮即缩放」 |
| 2 | 缩放是 `zoom×1.15` **离散跳变** | 目标位姿 + **每帧逼近**（0.3 比例 ≈ 4~5 帧收敛）；收敛那帧才提交 | `pose-store.test.ts`：单帧不 settled、`frames>1 && <60` |
| 3 | 平移**无惯性**，松手即停 | 松手按速度**惯性滑停**（摩擦 0.9 / 阈值 0.02 / 上限 2.5 px/ms） | `pose-store.test.ts`「松手后 pan 继续走」 |
| 4 | **单指 only**，`pointerdown` 只记一个 `pointerId`，捏合完全没实现 | **双指捏合缩放 + 双指平移**（距离→缩放、中心→平移） | `pointer-machine.test.ts` + `index.test.tsx` 捏合用例 |
| 5 | 无「双击空白放大」、无缩放控件 | 双击空白放大一档 + 内置 `+ / − / 复位`（**触屏唯一可见的缩放入口**） | `index.test.tsx` |

### 3.3 拖动抑制（旧实现踩过的三个回归点，本轮全部保留）

| 契约 | 在哪 | 测试 |

## 4. 「必须和传送点交互之后才可解锁传送」怎么落的

### 4.1 现状与目标的差别

| | 现状（服务端） | 新入口（本轮） |
| --- | --- | --- |
| 点亮时机 | **首次到达即自动** `waypoint_unlocked = true`（`map.service.ts`） | **必须在该节点与传送点交互** |
| 判定位置 | 服务端 `game_node_progress.waypoint_unlocked` | 前端会话来 `unlocked: Set<nodeCode>` |
| 服务端已点亮能否绕过 | — | **不能**：`travelDecision` **不读** `progress.waypointUnlocked` |

**测试守住这条**：夹具里南门的 `progress.waypointUnlocked = true`，未交互时按钮**仍然禁用**
（`MapLabPage.test.tsx` 的「即便服务端已 waypointUnlocked…」）。

### 4.2 完整链路（端到端有用例）

```
北门(起点) ──相邻──▶ 中转站 ──相邻──▶ 南门(有传送点)
   └─ 不相邻 ──────────────────────────┘
```

| 步 | 玩家可见因果 | 协议证据 |
| --- | --- | --- |
| ① | 在北门看南门 → 「暂不可前往」**禁用** + 「需先在此地与传送点交互」 | 无请求 |
| ② | 人不在南门 → **不给**交互按钮（防隔空点亮） | 无请求 |
| ③ | 北门 → 中转站 → 南门（两次相邻移动） | 两次 `map.enter` |
| ④ | 人在南门 → 出现「与传送点交互」→ 点击 → 「已点亮」（清单里那条同步变） | 纯前端 |
| ⑤ | 走开：南门 → 中转站 → **北门**（必须回到**不相邻**处，传送才有意义） | 两次 `map.enter` |
| ⑥ | 从北门看南门 → 「传送至此」**可点** → 点击 | **`map.waypoint`** |

> 第一版测试把「人在南门」和「传送到南门」写在同一场景里 —— 逻辑自相矛盾，被测试自己打回。
> 这条链路的正确形态必然是「**走到 A → 在 A 交互 → 走开 → 再传送回 A**」，已写进测试注释。

### 4.3 「可交互对象」三类来源不同（**这点必须记住**）

| kind | 来源 | 备注 |
| --- | --- | --- |
| `waypoint` 传送点 | **节点 `hasWaypoint`（前端派生）** | `game_map_objects` 今天**只有 `office`**；`14 §4.2` 的设计是把它做成 `kind='waypoint'` 的对象行。后端补上后**只需改 `lab-objects.ts` 一处** |
| `realm` 秘境入口 | **节点 `featureKey === 'realm'`（前端派生）** | 与旧面板同一判据（第八峰·后山） |
| `office` 职能入口 | **服务端 `game_map_objects`** | 藏经阁 / 丹霞院…原样透传 |

「随机刷新的怪物」**未进对象表**：`14 §4.3` 已判定它该走在线 tick（做成持久对象会开出
「离线也能刷」的口子）。本轮沿用该结论，未改。

### 4.4 ⚠️ 这是原型口径（已上屏警告）

- `unlocked` 是 **React state**，**刷新即回初始**；
- 页面顶部 `MapLabNotice` 常驻写明这一点 + 「持久化解锁需后端 `map.interact`」；
- 服务端仍是「到达即点亮」⇒ 新入口的门槛**严格更严**，不会让玩家获得服务端不认的能力；
  但从「已点亮的节点」出发传送时，服务端仍按它自己的 `waypoint_unlocked` 放行（**目前两者一致**，
  因为交互必须先走过去，走过去服务端就已经亮了）。
