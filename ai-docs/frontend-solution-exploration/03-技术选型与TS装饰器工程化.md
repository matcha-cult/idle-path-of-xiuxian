# 03 · 技术选型与 TS 装饰器工程化（React + MobX）

> 用户硬性要求：React + MobX；脚手架无倾向；**TypeScript 的注解/装饰器不能"老是出错"**。
> 本文件给出选型结论、装饰器三条经典坑的根因，以及一套开箱即用的配置。

---

## 1. 选型结论表

| 领域 | 选择 | 版本基线 | 理由 |
|---|---|---|---|
| 框架 | **React** | 18.x（稳妥）或 19.x | 硬性要求；生态成熟 |
| 脚手架 | **Vite（react-ts 模板）** | Vite 5/6 | esbuild 原生支持 `experimentalDecorators`，零额外插件；SPA 无 SSR 需求；dev 下 WS 代理一把过 |
| 状态 | **MobX 6 + mobx-react-lite** | mobx ^6.13、mobx-react-lite ^4 | 硬性要求；观察者模型天然贴合"服务器推送 → 局部状态更新" |
| 语言 | TypeScript | ^5.x（5.4+） | 启用装饰器见 §3；不用 reflect-metadata、不开 emitDecoratorMetadata（前端用不上，开了反而多一层错源） |
| 路由 | react-router | v6/v7 | 标准选择 |
| 测试 | vitest + @testing-library/react | 与 Vite 同栈 | mock IonetClient 的 adapter 即可跑全链路 |
| 包管理 | pnpm | 9 | 与仓库一致 |
| 代码规范 | eslint + prettier（typescript-eslint 插件） | 9.x / 3.x | 需要一条针对装饰器的规则开关（§4） |

**不建议 Next.js**：本项目是"长连接 + 常驻客户端状态 + 推送渲染"的 SPA 体感游戏，无 SSR/SEO 需求；Next 的 App Router 对装饰器/全局单例状态是负资产；且后期小程序端无法复用 SSR 管线。Vite SPA 是当前约束下的最优解。

## 2. 为什么"装饰器老是出错"——三条根因（先讲原理）

### 根因 1：`useDefineForClassFields` 与 legacy 装饰器互斥（最常见、最隐蔽）

- 当 `target >= ES2022` 时，TypeScript 默认 `useDefineForClassFields: true`，类字段走原生 `Object.defineProperty` 语义。
- MobX 6 legacy 装饰器（`@observable` 等）的设计前提是"字段先由装饰器接管，赋值在构造期完成"。若 `useDefineForClassFields: true`：
  1. 字段初始化表达式在**装饰器之后**执行；
  2. 原生 define 会把「实例自有的、值为 `undefined`/初始值」的字段**覆盖掉 observable 的访问器**；
  3. 结果：属性看起来存在但**不是响应式的**——UI 不更新、无任何报错，纯玄学 bug。

> **唯一正确组合（legacy 装饰器方案）**：
> ```jsonc
> "experimentalDecorators": true,       // 用旧版装饰器语法
> "useDefineForClassFields": false      // ★ 必须显式关掉，否则 MobX 响应式失效
> ```

### 根因 2：工具链对装饰器支持不一致

| 工具 | legacy 装饰器行为 | 注意 |
|---|---|---|
| tsc（typecheck） | ✅ `experimentalDecorators: true` | 无埋点 |
| esbuild（Vite 转译） | ✅ 自动读 tsconfig 的 `experimentalDecorators`/`useDefineForClassFields` | 默认值可能和 tsc 不一致，**必须两边都显式写** |
| vitest（esbuild） | ✅ 同上 | 同上 |
| babel（若引入 @vitejs/plugin-react 的 babel 路径） | ⚠️ 需 `@babel/plugin-proposal-decorators` 且 `legacy: true`，与 TS 语法不同源 | 尽量别混用 |
| 新版 TS 对 `experimentalDecorators` 的态度 | TS 5.x 仍完整支持（有废弃警告文档，无移除路线图） | 可长期用 |

> 实践铁律：**tsconfig、vite.config、vitest.config 三处的 `define` 语义保持一致；不要在同一构建里混用 babel 与 esbuild 两条装饰器管线。**

### 根因 3：装饰器"看得到但摸不着"的配置误区

- `@observer` 是 mobx-react-lite 的**组件装饰器**，其类型标注要求 tsconfig 里 `/* @jsx */` 无碍，但旧版 mobx-react 需要 `tsconfig` 的 `"jsx": "react"` 与 decorator 联合出问题——用 `mobx-react-lite` 则只涉及类组件装饰器，风险面小。
- 前端不需要 `emitDecoratorMetadata`/`reflect-metadata`（那是 NestJS/DI 场景）。不开它，就少一类"design:paramtypes undefined"的怪错。
- eslint 默认可能报 `@typescript-eslint/no-unsafe-decorator` 等误伤（TS5 + 新语法库），需要对应规则开关（§4）。

## 3. 三条路线（从"最稳"到"最现代"）

### 方案 A（推荐）：legacy 装饰器 + MobX 6 官方装饰器

与后端 ionet-ts / 服务端仓库的 tsconfig 风格完全一致（它们就是 `experimentalDecorators: true` + `emitDecoratorMetadata: true`），生态文档最厚、答疑最多，是"不会老是出错"的最优解。

```jsonc
// tsconfig.json（Vite react-ts 模板改造后）
{
  "compilerOptions": {
    "target": "ES2022",
    "useDefineForClassFields": false,      // ★★ 方案 A 的关键开关
    "experimentalDecorators": true,        // ★★ 启用 legacy 装饰器
    "module": "ESNext",
    "moduleResolution": "bundler",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "jsx": "react-jsx",
    "strict": true,
    "skipLibCheck": true,
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true,
    "isolatedModules": true,
    "noEmit": true
    // 注意：不要开 emitDecoratorMetadata，不需要 reflect-metadata
  },
  "include": ["src"]
}
```

```ts
// stores/player.store.ts —— 用法示例
import { makeObservable, observable, computed, action } from 'mobx';

export class PlayerStore {
  @observable spirit = 0;            // 灵韵
  @observable realmIndex = 0;
  @observable loading = false;

  constructor() { /* 全字段已装饰，无需 makeObservable(this,...) */ }

  @computed get realmName(): string { return REALMS[this.realmIndex]; }

  @action
  applyGain(delta: number) { this.spirit += delta; }
}
```

- 若个别 Store 需要无装饰器混合（如工具类），对**未装饰**的类用 `makeObservable(this, {...})` 显式声明即可，两者不冲突（同一类内要么全装饰、要么显式，别混）。
- 组件侧：`observer(Component)` 函数形式，比 `@observer` 装饰器更省心（函数组件主流），装饰器只留给 Store。

### 方案 B：标准（TC39）装饰器 + MobX 6.10+

- TS 5.2+ 支持标准装饰器：`"experimentalDecorators": false`（默认），`"useDefineForClassFields": true`（默认亦可显式）。
- MobX 6.10 起支持标准装饰器写法：`@observable` / `@computed` / `@action` 可以直接用。
- **已知限制（务必知悉再选）**：
  - 装饰器不可带参数：`@action.bound`、`@observable.struct` 这类「带参数的 legacy 形式」不可用 → action 不再自动绑定 `this`，需箭头函数或构造器内 `bind`；
  - 标准装饰器生态的调试信息/社区案例少于 legacy；MobX 对标准装饰器的支持标注为"可用、有边角限制"（如继承场景）。
- 适合"想一步到位 TS 官方路线"的团队，但**当前不是降低报错率的最优解**。

### 方案 C（兜底）：无装饰器

```ts
import { makeAutoObservable } from 'mobx';
export class PlayerStore {
  spirit = 0;
  realmIndex = 0;
  constructor() { makeAutoObservable(this); }   // 自动推断：属性=observable，方法=action，getter=computed
}
```

- 零装饰器：tsconfig 恢复默认，任何工具链零冲突——**这是"绝对不再出装饰器错"的终极保险**。
- 代价：失去显式装饰器表达力；对大型项目可读性略降。

> **结论推荐：方案 A 起步**（与后端仓库同风格、案例最多、报错面最小），并在 CI 里加一条 `tsc --noEmit` 卡死配置回归（§5）。若你预判团队将来会开标准装饰器，可跳到 B，但请先读限制清单。

## 4. 配套工程细节（防"莫名其妙报错"清单）

### vite.config.ts 显式对齐

```ts
// vite.config.ts
export default defineConfig({
  esbuild: {
    // 与 tsconfig 保持一致；Vite 会读 tsconfig，但显式声明可防工具链默认值漂移
    target: 'es2022',
    supported: { decorators: true },   // esbuild 已按 experimentalDecorators 处理，此处仅为显式意图
  },
  server: {
    proxy: {
      '/api': { target: 'http://localhost:3000', changeOrigin: true },
      '/ws':  { target: 'ws://localhost:3000', ws: true },   // ionet WS dev 代理
    },
  },
});
```

（若按仓库现状：`pnpm --filter idle-path-server dev` 起 3000 端口，前端 5173 全代理，天然同源无 CORS 烦恼。）

### eslint 规则开关（TS5 + decorators 常见误报）

```jsonc
"rules": {
  // 版本/语法误报开关（视 typescript-eslint 版本按需配置）
  "@typescript-eslint/no-unsafe-decorator": "off",
  "no-decorators": "off",
  "typescript/no-explicit-any": "warn"   // 与 data: unknown 载荷互转时的合理降级
}
```

### 常见报错排查表

| 症状 | 根因 | 处置 |
|---|---|---|
| 属性"不是响应式"，UI 不更新 | `useDefineForClassFields` 未关 | 置 `false`（§2 根因1） |
| `Property 'observable' does not exist` / 装饰器报红线 | tsconfig 未开 `experimentalDecorators` | 打开（§3 方案A） |
| 运行时 `TypeError: Cannot apply decorator` | babel/esbuild 管线混用 | 统一走 esbuild 或统一 babel legacy（§2 根因2） |
| `@observer` 组件类型报错 | 用了 mobx-react（旧）而非 mobx-react-lite；或泛型写法 | 用 `observer(Comp)` 函数形式（§3 方案A） |
| Vite 构建报 decorator 相关 transform 错 | vite config 里 esbuild target 过低 | `target: 'es2022'` |
| vitest 里装饰器正常、浏览器里异常 | 两处 tsconfig 不一致 | 统一基座 tsconfig（§5） |

## 5. 防回归基建（让"不会老是出错"可持续）

1. **单一基座 tsconfig**：`tsconfig.json`（应用）+ 继承 `tsconfig.base.json`，vite/vitest/typecheck 全从基座读取，杜绝分叉。
2. **CI 卡点**：`pnpm typecheck`（`tsc --noEmit`）+ `pnpm lint` + `pnpm test` 三连闸；任何人改 tsconfig 都必须先过这三道闸。
3. **依赖锁定**：mobx / mobx-react-lite / typescript / vite 用 pnpm catalog 或 lockfile 锁定；升级 TypeScript 大版本时，先跑全量 typecheck + 一个"装饰器冒烟用例"（一个含 `@observable/@computed/@action/@observer` 的最小 Store+组件测试）。
4. **装饰器冒烟用例示例**（写进 vitest，防工具链升级踩坑）：

```ts
// __tests__/decorator-smoke.test.tsx
import { observer } from 'mobx-react-lite';
import { render } from '@testing-library/react';

it('legacy decorators keep reactivity (smoke)', async () => {
  const store = new PlayerStore();
  const View = observer(() => <div data-testid="v">{store.spirit}</div>);
  const { getByTestId } = render(<View />);
  expect(getByTestId('v').textContent).toBe('0');
  store.applyGain(10);                       // @action
  expect(getByTestId('v').textContent).toBe('10');  // 若 useDefineForClassFields=true 此断言必挂
});
```
