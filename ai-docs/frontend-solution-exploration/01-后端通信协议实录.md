# 01 · 后端通信协议实录（源码级事实清单）

> 本文件全部结论来自对仓库内真实源码的阅读，不是猜测：
> - 后端框架源码：`vendor/ionet-ts/packages/**`（submodule，dev 分支）
> - 本项目后端集成：`packages/server/src/**`
>
> 前端设计必须以本文件的「线协议契约」为唯一事实依据。

---

## 1. 总体形态（一句话）

后端是 **NestJS（HTTP/REST）+ ionet-ts（WebSocket/Action）** 双通道：
- **REST 通道**：NestJS Controller，负责注册/登录/角色等"低频、可缓存、需要语义校验"的接口（当前仓库实际业务全走这里），全局前缀 `/api`，JWT 守卫。
- **ionet WS 通道**：`@nbb-ionet/extension-nestjs` 的 `IonetModule` 把 ionet Action 注册进 `BarSkeleton`，由 `WebSocketExternalServer`（基于 `ws`）对外提供 `{cmd, subCmd, data}` 消息路由，路径默认 `/ws`。

对应 Java 版 ionet 的形态：External Server 面向无数语言客户端，Logic 层跑 Action——**前端只认线协议，不认框架**。

---

## 2. Action 路由体系（服务端视角）

来源：`packages/core-framework/src/decorators/action-decorators.ts`、`.../core/action-command-parser.ts`、`packages/server/src/ionet/*.ts`

- 类级 `@ActionController(cmd)`、方法级 `@ActionMethod(subCmd)`，元数据 key：`ionet:action_controller` / `ionet:action_method`（reflect-metadata）。
- 方法参数约定：**第一个非 FlowContext 的参数就是 `data` 载荷**（`ActionParameterPosition.DATA`），`FlowContext` 注入会话能力（`bindingUserId` 等）。
- `BarSkeleton.execute({cmd, subCmd, data})` 是核心执行入口：
  - 路由未命中 → `{ errorCode: 404, errorMessage: 'Action not found...' }`
  - 业务抛异常 → `{ errorCode: 500, errorMessage }`
  - 成功 → `{ data: 返回值 }`
- 本项目 cmd 分段约定（`packages/server/src/ionet/cmd.ts`）：system=1 / auth=10 / character=20 / item=30 / skill=40 / economy=50 / idle=60 / story=70 / chaos=80，段宽 10，段内 subCmd 从 1 起，0 保留。

> 前端含义：`(cmd, subCmd)` 对全世界就是一个个"接口编号"，任何语言只要能收发信封都能调用。这就是"一个后端、无数前端"的根基。

## 3. 线协议信封（WS，JSON 文本帧，v1 事实）

来源：`packages/core-framework/src/protocol/message.ts`、`packages/external-server/src/websocket/ws-server.ts`、`.../external-server.ts`

### 3.1 请求（客户端 → 服务端）

```jsonc
// 模型定义（RequestMessage）
{
  "cmd": 30,          // 必须
  "subCmd": 1,        // 必须
  "data": { ... },    // 可选，业务载荷
  "headers": {},      // 模型中存在，但当前 ws-server 处理链丢弃，勿依赖
  "traceId": "..."    // 模型中存在，当前同样被丢弃
}
```

### 3.2 响应（服务端 → 客户端）

```jsonc
// 模型定义（ResponseMessage），服务端实际发送
{
  "data": { ... },        // 成功 payload
  "errorCode": 0,         // 0 / undefined = 成功
  "errorMessage": "..."   // 失败原因
  // headers 字段存在但服务端不填充
}
```

⚠️ **两个关键事实（对前端架构影响巨大）：**

1. **响应不回显 `cmd/subCmd`，也没有请求 ID**。`ws-server.ts` 对请求只取 `{cmd, subCmd, data}` 交给 `BarSkeleton.execute()`，响应只回 `{data, errorCode, errorMessage}`。
2. **`headers/traceId` 在 WS 处理链中被丢弃**（`handleMessage` 未透传）。协议模型里有，路上没有。

> 结论：**同一连接上若同时有多个未决请求，前端无法把响应与请求对应起来。** 这是"串行请求队列"策略的由来（详见 02 号文档 §3.2）。

### 3.3 错误码语义（现状）

| errorCode | 含义 | 场景 |
|---|---|---|
| `undefined` 或 `0` | 成功 | 正常返回 |
| `400` | 消息无法解析 | 服务端 JSON.parse 失败（本次发的是坏帧） |
| `404` | Action 未注册 | cmd/subCmd 组合不存在 |
| `500` | 内部异常 | Action 抛错 / 业务错误（业务错误码由后端扩展） |

> 前端应把 errorCode 归一到统一异常类型，业务层只认 `errorCode !== 0` 即失败。

## 4. WebSocket 通道行为

来源：`packages/external-server/src/websocket/ws-server.ts`

| 项 | 事实 |
|---|---|
| 库 | `ws`（npm ws@8） |
| 路径 | 默认 `/ws`（可配 `path`） |
| 部署 | 独立端口模式 / attach 模式（挂 NestJS http.Server，单端口三合一） |
| 帧类型 | **文本帧**，`data.toString()` 后 JSON 解析（默认 JSON codec） |
| 心跳 | 服务端每 30s `ws.ping()`（`heartbeatInterval`），2 个周期无 pong 则 `terminate()` |
| 推送 | `broadcast(message, exclude?)` 群发、`sendTo(userId, message)` 定点推送；编码传入的对象，**信封形状由调用方决定** |
| 连接态 | 无握手鉴权钩子（TS 移植版暂缺 Java 版 UserHook 类能力），鉴权需走"连接后首个 Action"或由后端另行加固 |

> 重要：**心跳 ping/pong 走 WS 协议层，浏览器 JS 完全观察不到**（浏览器自动回 pong 但不派发任何事件）。因此前端判断"连接是否还活着"不能靠 ping/pong，需要**应用层心跳**（调用 system 段 ping Action 并等待响应，见 02 号文档 §3.3）。

## 5. 编解码 SPI（协议可插拔）

来源：`packages/core-framework/src/protocol/protocol-codec.ts`、`.../json-codec.ts`、`packages/extension-jprotobuf/src/protobuf-codec.ts`

```ts
interface ProtocolCodec<T = unknown> {
  encode(data: T): Uint8Array | string;
  decode(buffer: Uint8Array | string): T;
  readonly contentType: string;
}
```

- **默认 JSON**：`JsonProtocolCodec`，contentType `application/json`，文本帧。
- **jprotobuf 扩展**（`extension-jprotobuf`）：基于 `protobufjs`，contentType `application/x-protobuf`，**二进制帧格式为自描述前缀 + protobuf 载荷**：

```
[1 字节 typeName 长度][typeName ASCII][protobuf 消息字节]
```

- 服务端编解码在 `ExternalServerOptions.codec` 一处注入——**换协议对前端而言只是换一个 EnvelopeCodec 实现**（02 号文档 SDK 设计已预留该扩展点）。

> 前端风险提示：jprotobuf 的"类型前缀自描述"格式目前是 ionet-ts 移植版私有设计（非标准 protobuf 流），若后端启用二进制协议，前端需要与后端对齐类型名注册表（typeName ↔ 消息结构映射）。

## 6. HTTP/REST 通道（本项目现状）

来源：`packages/server/src/main.ts`、`src/app.module.ts`、`src/modules/auth/*`、`src/modules/ws/*`

- NestJS 10，`app.setGlobalPrefix('api')`，端口 `PORT ?? 3000`。
- 全局 `APP_GUARD` = `JwtAuthGuard`（未打 `@Public` 的接口都要 JWT）。
- 现有接口：`POST /api/auth/register`、`POST /api/auth/login`、角色/物品/功法/境界等 REST 资源接口。
- **ionet-ts 的 HTTP/WS 外部服务当前被显式关闭**：`IonetModule.forRoot({ actions:[HealthAction], httpServer:false, wsServer:false, redis:false })`；`/ws-user` 只是 NestJS `@nestjs/platform-ws` 的预留入口（连接即返回一句提示，无业务）。
- `extension-nestjs` 有硬性保护：`NODE_ENV=production` 时拒绝启动（注释明示"生产请用 Java External Server"）。

> 前端含义：**后端当前业务 100% 在 REST 上，ionet WS 通道是"预留/将启用"**。所以前端 v1 必须 REST 与 WS 双通道都能跑，且两者职责划分（什么走 REST、什么走 Action）由后端决定——前端只提供两个通道的统一入口（02 号文档 §2）。

## 7. Codegen 产物形态（类型同步的来源）

来源：`packages/extension-codegen/src/typescript-generator.ts`、`.../action-scanner.ts`

`scanActions(actions)` + `TypeScriptCodeGenerator.generate()` 产物：

```ts
export const Commands = {
  HealthAction: { cmd: 1, ping: 1 },
} as const;

export interface HealthActionPingRequest { cmd: 1; subCmd: 1; data: unknown; }
export interface HealthActionPingResponse { cmd: 1; subCmd: 1; data: { status: string; service: string }; }
```

⚠️ **已知不一致**：生成器给 Response 接口带上了 `cmd/subCmd` 字段，但**线协议响应并不回显 cmd/subCmd**（见 §3.2）。因此：

- Codegen 产物（Commands 常量 + DTO 接口）适合作为**前端 API 层的类型参考**，可用脚本同步进前端仓库；
- 但**前端线协议 DTO 必须独立维护**（以本文件 §3 的契约为准），不能盲目信任生成接口。

## 8. 广播 / 推送

来源：`packages/core-framework/src/broadcast/types.ts`、`ws-server.ts`

- 框架抽象层的广播信封是 `BroadcastMessage { type, data, timestamp, fromUserId? }`——`type` 为字符串事件名，**与 `(cmd, subCmd)` 编码体系完全并列**。
- `WebSocketExternalServer.broadcast()` 对传入对象原样 encode 发送，信封由调用方决定：可能是 `{cmd, subCmd, data}`、可能是 `{type, data}`。
- **前端 SDK 的推送路由必须对两种信封都容错**：优先按 `cmd/subCmd` 路由，没有则回退按 `type` 路由；这是向后兼容的关键（乐观但稳妥的设计）。

## 9. 禁导入红线的实证

`packages/core-framework/src/core/flow/flow-context.ts` 第 1 行：

```ts
import { AsyncLocalStorage } from 'node:async_hooks';
```

core-framework / external-server / redis 等包面向 Node 运行时。**浏览器构建一旦 import `@nbb-ionet/*` 必然爆炸。**

> 铁律：**前端严禁 import 任何 `@nbb-ionet/*` 包。** 前端自建一个零运行时依赖的 `ionet-client` SDK，用本地声明的信封类型（与 §3 契约一致）+ 平台 Socket 适配器实现（02 号文档）。这与"前后端零耦合"恰好同构。

## 10. 客户端必须遵守的契约（v1 JSON，汇总）

1. 连接地址：`ws(s)://<host>[:port]/ws`（以实际部署为准，开发期可为 `ws://localhost:3000/ws`，经 Vite proxy 同源）。
2. 帧格式：文本帧，UTF-8 JSON；请求信封 `{cmd, subCmd, data?}`；响应信封 `{data?, errorCode?, errorMessage?}`。
3. 一次一请求（串行队列）或做好无关联响应处理；响应与请求无法靠信封字段配对（v1）。
4. 心跳：客户端应用层心跳（建议复用 system 段 ping Action），周期 ≤ 服务端 `heartbeatInterval`（30s）之半，即 15s 左右。
5. 断线：服务端 30s 无 pong 即踢；客户端重连后需重新完成鉴权/登录流程。
6. 推送：服务端可能随时下发 `cmd/subCmd` 信封或 `type` 信封，前端订阅路由两者都要接。
7. 错误：`errorCode !== 0` 一律视为失败，先按 400/404/500 兜底映射，业务错误码由后端后续扩展（前端做统一转译）。
8. 类型：DTO 以本契约为准；codegen 产物只作 API 层参考同步，不直接当线协议真相。
