## 1. 总体形态（一句话）

后端是 **NestJS（HTTP/REST）+ ionet-ts（WebSocket/Action）** 双通道：
- **REST 通道**：NestJS Controller，负责注册/登录/角色等"低频、可缓存、需要语义校验"的接口，全局前缀 `/api`，JWT 守卫。
  > 【已过时】原文称"当前仓库实际业务全走这里"。**当前事实**：REST 仅 3 个 controller —— `auth`（注册/登录）、`character`（建号/查询）、`health`；其余全部游戏交互走 WS（见 §6）。
- **ionet WS 通道**：`@nbb-ionet/extension-nestjs` 的 `IonetModule` 把 ionet Action 注册进 `BarSkeleton`，由 `WebSocketExternalServer`（基于 `ws`）对外提供 `{cmd, subCmd, data}` 消息路由，路径默认 `/ws`。
  > **当前事实**：WS **已启用**并 attach 到 NestJS `http.Server`（`attachNestServer: true, path: '/ws'`），注册 12 个 Action 类，握手期鉴权。

对应 Java 版 ionet 的形态：External Server 面向无数语言客户端，Logic 层跑 Action——**前端只认线协议，不认框架**。

## 2. Action 路由体系（服务端视角）

来源：`packages/core-framework/src/decorators/action-decorators.ts`、`.../core/action-command-parser.ts`、`packages/server/src/ionet/*.ts`

- 类级 `@ActionController(cmd)`、方法级 `@ActionMethod(subCmd)`，元数据 key：`ionet:action_controller` / `ionet:action_method`（reflect-metadata）。
- 方法参数约定：**第一个非 FlowContext 的参数就是 `data` 载荷**（`ActionParameterPosition.DATA`），`FlowContext` 注入会话能力（`bindingUserId` 等）。

  | cmd | 段 | cmd | 段 | cmd | 段 |
  |---|---|---|---|---|---|
  | 1 | system | 60 | skill | 110 | quest |
  | 10 | auth（HTTP，占位不注册 Action） | 70 | economy | 120 | story |
  | 20 | character（HTTP，占位不注册 Action） | 80 | realm | 130 | idle |
  | 30 | item | 90 | combat | | |

  > 原文的 `chaos` 段**不存在**；`skill/economy/idle/story` 段号全错。`system.ping = (1,1)` 存在且**在免鉴权白名单**（`PUBLIC_ACTION_KEYS`）。

> 前端含义：`(cmd, subCmd)` 对全世界就是一个个"接口编号"，任何语言只要能收发信封都能调用。这就是"一个后端、无数前端"的根基。

## 3. 线协议信封（WS，JSON 文本帧，v1 事实）

来源：`packages/core-framework/src/protocol/message.ts`、`packages/external-server/src/websocket/ws-server.ts`、`.../external-server.ts`

### 3.1 请求（客户端 → 服务端）

```jsonc
// 模型定义（RequestMessage）—— 当前（PROTOCOL.md §3）
{
  "cmd": 30,          // 必须
  "subCmd": 1,        // 必须
  "data": { ... },    // 可选，业务载荷
  "headers": {},      // 可选，已透传到 FlowContext（Action 可经 ctx.getRequest()?.headers 读）
  "traceId": "...",   // 可选，已透传
  "reqId": "r-1"      // 可选，★ 新协议：带上即可并发与精确配对
}
```

> 【已过时】原文称 `headers/traceId`"在处理链中被丢弃，勿依赖"——**已修复**（P0-2 落地），现经 `BarSkeleton.execute` 透传到 `FlowContext`。

### 3.2 响应（服务端 → 客户端）

```jsonc
// 当前（PROTOCOL.md §4）
{
  "data": { ... },        // 成功 payload
  "errorCode": 0,         // 0 / 缺失 = 成功
  "errorMessage": "...",  // 失败原因
  "reqId": "r-1",         // ★ 仅当请求携带 reqId 时回显
  "kind": "response"      // ★ 仅当请求携带 reqId 时写入
}
```

⚠️ **当前关键事实：**

1. **响应仍不回显 `cmd/subCmd`**；但**已支持 `reqId` 回显 + `kind='response'`**（请求带 `reqId` 时）。
   - 带 `reqId` 的请求 → 同连接可**并发**多个未决请求，客户端精确配对（A3 已提供 `RequestResponseAssociator`）。
   - 不带 `reqId` 的旧客户端 → 响应**逐字节不变**（无 `reqId`/`kind`），只能串行。
2. `headers` 服务端不回填；但请求侧的 `headers/traceId` 已透传到 `FlowContext`。

> 【已过时】原文结论"无法把响应与请求对应起来，只能串行队列"——**已修复**。当前默认应使用 **`reqId` 并发**，串行降为兜底（详见 [06 §1 S3](./06-现状校正与实施基线（2026-09-13）.md)、02 §3.2）。

### 3.3 错误码语义（传输层）

| errorCode | 含义 | 场景 |
|---|---|---|
| `undefined` 或 `0` | 成功 | 正常返回 |
| `400` | 消息无法解析 | 服务端 JSON.parse 失败（本次发的是坏帧） |
| `404` | Action 未注册 | cmd/subCmd 组合不存在 |
| `500` | 内部异常 | Action 抛错 |

> ⚠️ **重大遗漏补充（原文仅写"`errorCode !== 0` 即失败"是不完整的）**：
> 本项目 Action **不抛异常**，统一返回 `{ success, message, data? }`，被包进响应信封的 `data` 字段。
> 因此**业务失败时 `errorCode` 仍为 `0`**，表现为 `data.success === false` 且 `data.data.code` 为业务码
> （`UNAUTHORIZED` / `INVALID_PARAM` / `CHARACTER_NOT_FOUND` / `FORBIDDEN`，见 `packages/server/src/ionet/action-support.ts`）。
>
> **前端判定顺序**：① `errorCode !== 0` → 传输层错误；② `data.success === false` → 业务错误（读 `data.data.code`）；③ 成功。
> 只看 `errorCode` 会把全部业务失败当成功。详见 [06 §2](./06-现状校正与实施基线（2026-09-13）.md)。

## 4. WebSocket 通道行为

来源：`packages/external-server/src/websocket/ws-server.ts`

| 项 | 事实（2026-09-13 校正后） |
|---|---|
| 库 | `ws`（npm ws@8） |
| 路径 | 默认 `/ws`（可配 `path`）；本项目 `attachNestServer: true, path: '/ws'` |
| 部署 | 独立端口模式 / attach 模式（本项目挂 NestJS `http.Server`，单端口三合一） |
| 帧类型 | **文本帧**，`data.toString()` 后 JSON 解析（默认 JSON codec） |
| 心跳 | 服务端每 30s `ws.ping()`（`heartbeatInterval`），2 个周期无 pong 则 `terminate()` |
| 握手鉴权 | ✅ **已有**（P1-2 落地）：`authenticate({headers, url, protocol})` 在 upgrade 阶段调用；返回 `null` → HTTP 401 拒升级；成功 → 绑定 `userId`、预置 `FlowContext`、登记连接注册表。本项目支持 `Bearer` 与 `?token=`（`PROTOCOL.md §6`） |
| 定向推送 | ✅ **已修复**（P0-4 落地）：`sendNotification(userId, …)` 可用；`connectionRegistry` 维护"已绑定 userId → 扇出 Connection"。本项目 `verify:sendto` 实测 PASS |
| 广播抽象 | ✅ **已接线**（P0-5 落地）：`IonetModule` 默认提供并导出 `IONET_BROADCASTER`（`broadcaster: false` 可关） |
| 推送入口 | 规范化入口 `broadcastNotification` / `sendNotification` / `Broadcaster.*`，一律经 `createNotificationMessage()` 构造、**必带 `kind='notification'`**。兼容保留的 `broadcast(unknown)`/`sendTo(unknown)` 仍裸透传（不保证带 `kind`），新代码勿用 |

> 【已过时】原文表格中"推送：`sendTo` 当前失效，永远返回 false"、"无握手鉴权钩子"、"广播抽象未接线到 WS 传输，当前不可用"——**三条均已修复**（2026-09-13），详见 [06 §1 S4/S5](./06-现状校正与实施基线（2026-09-13）.md)。

> 重要：**心跳 ping/pong 走 WS 协议层，浏览器 JS 完全观察不到**（浏览器自动回 pong 但不派发任何事件）。因此前端判断"连接是否还活着"不能靠 ping/pong，需要**应用层心跳**（调用 `system.ping (1,1)` Action 并等待响应，该 Action **免鉴权**，见 02 号文档 §3.3）。

## 5. 编解码 SPI（协议可插拔）

来源：`packages/core-framework/src/protocol/protocol-codec.ts`、`.../json-codec.ts`、`packages/extension-jprotobuf/src/protobuf-codec.ts`

```ts
interface ProtocolCodec<T = unknown> {
  encode(data: T): Uint8Array | string;
  decode(buffer: Uint8Array | string): T;
  readonly contentType: string;
}
```

- **默认 JSON**：`JsonProtocolCodec`，contentType `application/json`，文本帧。
- **jprotobuf 扩展**（`extension-jprotobuf`）：基于 `protobufjs`，contentType `application/x-protobuf`，**二进制帧格式为自描述前缀 + protobuf 载荷**：

```
[1 字节 typeName 长度][typeName ASCII][protobuf 消息字节]
```

- 服务端编解码在 `ExternalServerOptions.codec` 一处注入——**换协议对前端而言只是换一个 EnvelopeCodec 实现**（02 号文档 SDK 设计已预留该扩展点）。

> 前端风险提示：jprotobuf 的"类型前缀自描述"格式目前是 ionet-ts 移植版私有设计（非标准 protobuf 流），若后端启用二进制协议，前端需要与后端对齐类型名注册表（typeName ↔ 消息结构映射）。

### 6.1 第三通道：ionet HTTP External Server（同路由的第二传输，**代码就绪、本项目未启用**）

来源：`packages/external-server/src/http/http-server.ts`、`packages/external-server/README.md`、`PROTOCOL.md §9/§9.1`

- 路由：`POST /{prefix}/{cmd}/{subCmd}`，`prefix` 默认 `/api`（如 `POST /api/1/1` 即 cmd=1、subCmd=1）；**`pathPrefix` 可配**（P2-2，例 `/ionet`）。
- 请求体：经 codec 解码；**裸 DTO 与 `{ "data": {...} }` 包装两种都接受**。
- 响应：与 WS **完全相同的信封** `{data?, errorCode?, errorMessage?}`；HTTP 状态码 = `errorCode >= 400 ? errorCode : 200`。
- 失败语义：路径不合法 → 404；body 解析失败 → 400；未就绪 → 503。
- ⚠️ **HTTP 通道不产生 `reqId`/`kind`**（`PROTOCOL.md:180`）→ 降级后**并发关联能力丢失**，只能串行。

> 前端价值：**潜在韧性兜底**——企业代理/弱网/部分小程序不支持 WS 时，可降级为 HTTP 调用同一批 Action。前端 SDK 值得预留 `HttpFallbackTransport`（05 §P2-2）。
> ⚠️ **前置条件（原文称"零后端改动"不准确）**：本项目当前 `httpServer: false`（`app.module.ts:65`），**必须先在后端开启并配置独立前缀**才可用。
> ⚠️ 默认前缀 `/api` 会与 NestJS REST 的 `/api` **冲突**，同机部署必须分前缀（如 REST `/api`、ionet HTTP `/ionet`）。列为开放问题 Q9。

## 8. 广播 / 推送

来源：`packages/core-framework/src/broadcast/types.ts`、`ws-server.ts`、`PROTOCOL.md §5/§10`

- **当前规范推送信封**（唯一构造入口 `createNotificationMessage()`）：

  ```jsonc
  { "kind": "notification", "cmd"?: 100, "subCmd"?: 1, "type"?: "room.tick",
    "data": {…}, "timestamp": 1700000000000, "headers"?, "reqId"?, "fromUserId"? }
  ```

  `type`（字符串事件名）与 `cmd/subCmd` 编码体系**并列可选**——按 `cmd/subCmd` 路由时给前者，按事件名路由时给 `type`。
- 服务端规范化推送入口：`broadcastNotification(notification, exclude?)`、`sendNotification(userId, notification)`、`Broadcaster.*`。
- **兼容路径**：`broadcast(unknown)` / `sendTo(unknown)` 仍对传入对象**原样 encode**（形状由调用方决定，不保证带 `kind`）。旧代码可能发 `{cmd,subCmd,data}` 或 `{type,data}`。
- 【已过时】原文的 `BroadcastMessage {type, data, timestamp, fromUserId?}` 仅描述 core-framework 抽象层；当前应用层应以 `kind='notification'` 信封为准。

> **前端 SDK 的推送路由**：优先按 `kind === 'notification'` 分流（A3 `classifyFrame` / `isNotificationFrame` 已提供），再按 `cmd/subCmd`、无则按 `type` 路由。对裸透传的旧形状保留容错（向后兼容的关键）。
> ⚠️ 注意判别值实际是 **`'notification'`**，不是早期文档设想的 `'push'`（见 [06 §1 S8](./06-现状校正与实施基线（2026-09-13）.md)）。

## 10. 客户端必须遵守的契约（当前，JSON，汇总）

> 规格源：`vendor/ionet-ts/PROTOCOL.md`。以下为前端视角的收敛版。

1. **连接地址**：`ws(s)://<host>[:port]/ws`（开发期 `ws://localhost:3000/ws`，经 Vite proxy 同源）。
2. **鉴权**：握手段带 `?token=<jwt>`（浏览器唯一可行通道；Node 客户端可 `Authorization: Bearer`）。失败 → HTTP 401 拒升级。
3. **帧格式**：文本帧 UTF-8 JSON；请求 `{cmd, subCmd, data?, headers?, traceId?, reqId?}`；响应 `{data?, errorCode?, errorMessage?, reqId?, kind?}`。
4. **关联**：为每个请求生成 **`reqId`** → 服务端回显 `reqId` + `kind='response'`，同连接**可并发**。不带 `reqId` 则退化为串行（兼容旧行为）。
5. **心跳**：客户端**应用层**心跳，复用 `system.ping (1,1)`（**免鉴权**），周期 ≤ 服务端 `heartbeatInterval`（30s）之半，即 15s 左右；超时判死链 → 主动重连。
6. **断线**：服务端 30s 无 pong 即踢；客户端重连后需**重新完成握手鉴权**。
7. **推送**：服务端下发 `kind='notification'` 信封（可能带 `cmd/subCmd` 或 `type`）；按 `kind` 分流后再按 `cmd/subCmd`，无则按 `type`。对旧式裸透传形状容错。
8. **错误**：**必须两级判定** —— ① `errorCode !== 0` 为传输层失败（400/404/500）；② `data.success === false` 为**业务失败**（读 `data.data.code`）。只看 `errorCode` 会漏判全部业务错误。业务码表（Q5）待后端补齐。
9. **类型**：线协议类型用 `@nbb-ionet/client-protocol`（唯一白名单包）；业务 DTO 由 codegen 产物同步，信封**不重复定义**。
