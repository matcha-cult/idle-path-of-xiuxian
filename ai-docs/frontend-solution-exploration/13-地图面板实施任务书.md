# 13 · 地图面板实施任务书（青云宗实践样板）

> 设计依据：`settings-revision-2.md` §5（地图线路图与传送点）/ §6（战斗结算）/ §7（青云宗）。
> 硬约束：`11-面板重做进度与接续手册.md` §4 —— **组件能抽就抽，坚决不允许单文件聚合无数组件实现一个页面**。
> 地位：这是**地图层的第一个面板**，也是后续地图（山下凡尘 / 混沌裂隙）的模板 —— 它长什么样，
> 后面两张图就照什么样长。因此本任务书同时也是「地图面板的形态定稿」。

---

## 1. 面板要回答的三个问题（沿用「问题驱动三段式」）

| 玩家的问题 | 面板给出什么 |
| --- | --- |
| 我在哪、能去哪？ | **线路图**：当前节点高亮、已发现节点可选、未发现节点不显示（服务端不下发） |
| 去了能干什么？ | **节点详情**：怪物境界、战力门槛（与我的战力对比）、传送点状态、承载的系统入口 |
| 打过了算解锁了吗？ | **三态徽标**：已到达 / 传送点已点亮 / **已解锁离线挂机** |

## 2. 组件拆分（**按 §4 硬要求，页面只做编排**）

```
packages/web/src/pages/game/panels/
├── MapPanel.tsx                    容器：store → props 映射 + 三段式编排（≤200 行）
├── MapPanel.test.tsx
└── map/
    ├── MapRouteCard.tsx            线路图卡（节点 + 邻接的可视化）
    ├── MapRouteCard.test.tsx
    ├── MapNodeCard.tsx             单节点卡（名称/境界/门槛/我的战力/状态/动作）
    ├── MapNodeCard.test.tsx
    ├── MapNodeBadge.tsx            三态徽标（已到达 / 传送点 / 离线挂机已解锁）
    ├── MapNodeBadge.test.tsx
    ├── FeatureGate.tsx             「未开放」统一渲染（feature_key 无对应系统时）
    ├── FeatureGate.test.tsx
    ├── feature-registry.ts         **客户端**判断 featureKey 是否已实现
    ├── feature-registry.test.ts
    ├── presentation.ts             纯函数：文案/排序/门槛对比/环层分组
    └── presentation.test.ts
```

**拆分的判据（不是凑数）**：

- `MapRouteCard` 与 `MapNodeCard` 是**两个不同的信息层级**（全景 vs 单体），复用的只有徽标；
- `MapNodeBadge` 会被两处用到（线路图的小点 + 详情卡），**抽出来才有复用价值**；
- `FeatureGate` 是**跨域通用件**：地图上任何承载未实现系统的节点（丹霞院/灵兽苑/天刑台…）
  都走它，后续地图 2/3 直接复用 —— 这是本面板最值得抽的一件；
- `feature-registry.ts` 与 `presentation.ts` 是纯逻辑，必须与组件分离（可单测，不 render）。

若落地时某文件超过 200 行（web hygiene 门禁），**继续往 `map/` 里拆，不要压行**。

## 3. Store 契约（`packages/web/src/stores/map-store.ts`）

```ts
class MapStore {
  maps: MapView[];                  // 地图列表（当前只有青云宗）
  nodes: MapNodeView[];             // 已发现节点（服务端已过滤未发现的）
  edges: MapEdgeView[];             // 邻接表
  progress: NodeProgressView[];     // 该角色在节点上的三态
  currentCode: string | null;       // 当前所在节点
  loading: boolean;
  error: string | null;

  load(): Promise<void>;
  enter(nodeCode: string): Promise<void>;     // 跑图（确定性战力检定在服务端）
  waypoint(nodeCode: string): Promise<void>;  // 传送到已点亮节点
}
```

- **挂载时不拉取**：首屏由 `RootStore.loadPanel()` 并发加载（需把 `map.load()` 加进 `loadPanel()`）。
- 三态交给 `AsyncBoundary`；业务失败（`NODE_LOCKED` / `NODE_POWER_NOT_ENOUGH` /
  `WAYPOINT_NOT_UNLOCKED`）走 store 既有错误出口，**不要在面板里重判协议**。
- `RootStore` 需要新增 `map: MapStore` 并加进 `loadPanel()` 的并发数组。

## 4. feature-registry：**「是否实现」是客户端的判断**

`feature_key` 是数据（服务端只描述「这里是什么」），**「这个系统做了没」是代码事实**，
所以判断必须落在客户端的 registry 里，不能写进数据库（否则种子会随实现进度腐烂）：

```ts
// 已实现的系统 → 给出跳转/内嵌方式；未实现的 → undefined（渲染 FeatureGate「未开放」）
export const FEATURE_PANELS: Partial<Record<FeatureKey, string>> = {
  skill: 'skill',      // 藏书阁 / 传功崖 → 功法面板
  craft: 'economy',    // 百器阁 → 通货·炼器面板
  quest: 'quest',      // 执事堂 → 任务面板
  // alchemy(丹霞院) / beast(灵兽苑) / farm(灵田药园) / pvp(天刑台) /
  // discipline(戒律堂) / profession(七职业峰) → 尚未实现，走 FeatureGate
};
```

> ⚠️ `farm`（灵田药园）虽未实现，但它是 `kind: 'idle_spot'`，**必须仍可作为挂机目标** ——
> 「承载的系统未实现」与「能不能挂机」是两件事，不要因为 `farm` 未实现就把挂机点禁掉。
> 这条要写成测试。

## 5. 测试要求（每个文件同目录测试，≥5 例/组件）

必覆盖：
- 线路图：只渲染**已发现**节点（服务端不下发未发现的，但面板也不能自己造）；当前节点高亮；
  分组按 `ring`（外环/接引/八峰/内环/主峰）；
- 节点卡：战力门槛与「我的战力」对比正确（**恰好等于门槛要显示为可进入**，差 1 显示不足）；
- 三态徽标：三种状态各自的文案与语义色；
- `FeatureGate`：未实现的 6 个 feature 都渲染「未开放」且**禁用入口**；
- **灵田药园（未实现系统 + 挂机点）仍可作为挂机目标**（第 4 节的 ⚠️）；
- 交互：点节点 → 真的发出 `MAP_CMD.enter`（常量从 `@idle-path/ionet-transport` 导入，**禁止字面量**），
  点传送 → `MAP_CMD.waypoint`；交互用例必须先 `await harness.connect()`；
- 断言页面文本**不含协议字段**（node `code`、`feature_key` 原文、ISO 时间串）；
- 边界：`nodes`/`edges` 为空、`currentCode` 为 null、边引用了未下发的节点（**不能崩**）。

## 7. 主线的翻牌决定（2026-09-13 定）

`panel-registry.tsx` 的改动**由主线做**，取值已定，避免后续再讨论：

| 项 | 取值 | 理由 |
| --- | --- | --- |
| key | `map` | 与后端 `MAP_CMD` 段一致 |
| label | **地图** | 玩家视角的容器名；「秘境」是其中的一种节点 |
| group | **`campaign`（征伐）**，且排在**组内第一项** | 按玩法因果链：先看地图（在哪打）→ 再进秘境（打什么）→ 挂机（自动化的它）→ 战斗图鉴（数据） |
| icon | **`GlobalOutlined`**（已确认该图标存在） | 表达「世界/线路图」，与「秘境」的 `CompassOutlined` 不撞 |

**同时记录一处待办（不在本轮范围）**：地图面板上线后，**独立的「秘境」域会与地图面板里的秘境节点重叠**
（后山峰会同时出现在两个面板）。倾向的收口方式是「把秘境从侧栏撤掉、由地图面板内嵌秘境详情」，
但那是导航结构改动，**等用户定**（见 R2 §7.7 的相关条目）。本轮先并存。

## 8. 阶段状态（2026-09-13 · 用户验收后）

**用户结论（逐字要点）**：地图的**功能与实现通过**；但 **UI 表现形式需要大调整**，
**后端可能也需要随之调整**。

因此本文 §2~§5 描述的是**当前已落地的实现形态**，它即将被重做。重做时请注意：

| 部分 | 重做时是否仍可复用 |
| --- | --- |
| **§2 的组件边界**（`MapRouteCard` / `MapNodeCard` / `MapNodeBadge` / `FeatureGate` + `presentation.ts` / `feature-registry.ts`） | **大概率可复用** —— 它是按「信息层级 + 复用点」切的，不是按视觉切的；换表现形式通常只是换容器与排版 |
| **`FeatureGate` + `feature-registry.ts`** | **务必保留** —— 「系统是否已实现」的客户端判定是跨地图通用件，与表现无关 |
| **§3 store 契约**（`load` / `enter` / `waypoint` + `playerPower`） | 取决于后端是否改协议；若只改展示则不动 |
| **§4~§5 的视觉形态**（按 `ring` 五层分组、卡片式节点、Tooltip 文案等） | **预期被推翻**，不要为保持它而妥协 |
| **本文 §7 的侧栏取值**（key/label/group/icon） | 若表现层调整涉及导航结构，一并重议 |

**待用户给出方向**（压缩后第一件事就是问这个）：
1. 表现形式的**目标形态**是什么（线路图的视觉隐喻：星图 / 卷轴 / 层叠剖面 / 纯列表？）；
2. 是否需要**后端配合**（例如：地图/节点的额外字段、当前所在节点持久化、位置与坐标信息、探索进度的实时推送）；
3. §7 遗留的那个决定：**「秘境」面板是否从侧栏撤掉**、由地图面板内嵌秘境详情。

> 实现仍以「组件能抽就抽」为准（`11-...md` §4）：重做表现层时**继续往 `panels/map/` 拆**，
> 不要把新的视觉堆回 `MapPanel.tsx`。

## 9. 目标形态已定（2026-09-13 晚）→ 转 `14-地图画布方案探讨.md`

上节三个问题，用户已给出前两个的答复：

> 「我之所以以字符画形式描述了地图，就是希望能以**画布方式，或者伪画布渲染地图节点**。
> 请探讨方案：**大地图以 n×n 格子定义，然后地图节点就落于某个具体的格子**，这样前端可以
> 接受后端地图定义，直接使用 antd 组件去渲染。**进入地图之后，加载目标地图的可交互对象**，
> 如 npc、传送点、秘境入口，甚至是随机刷新的怪物。总体设想是，在 pc 端，**左边地图网格，
> 右边地图内可交互对象**，也就是说，**必须和传送点交互之后才可解锁传送**。」

| 上节问题 | 答复 |
| --- | --- |
| 1. 表现形式的**目标形态** | **n×n 格子棋盘 / 伪画布**；PC 左格右对象；移动端另议 |
| 2. 是否要**后端配合** | **要** —— 节点需坐标、地图需行列数、新增可交互对象层、传送点改为交互解锁 |
| 3. 「秘境」面板是否撤出侧栏 | ⏳ **仍未定**，继续挂起 |
